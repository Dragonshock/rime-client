## 定稿走真实路径（2026-11-14，见 055）

`voice-mlx::transcribe_finish` 那张 64 均值 8x8 图已经删掉。现在定稿走
`voice-mlx::transcribe(model_dir, pcm)`：

1. `voice-mel` 出 `(128, frames)` 梅尔；
2. `AudioTower::open` + `encode_mel` 出 `(audio_tokens, 1024)`；
3. `voice-tokenizer` 按参考模板拼提示（`language Chinese<asr_text>`），音频占位个数取编码器实际行数；
4. `TextDecoder::prefill` 之后逐步喂 1 个 token，键值写进 28 层的 KV 缓存，全词表 argmax；
5. 遇到 `151643`（`<|endoftext|>`）或 `151645`（`<|im_end|>`）停下，最多 256 个新 token；
6. 还原文本时去掉特殊 token 的字面量。

`WeightDecoder` 定稿时把累积样本交给这条路径，`StepOutput` 里的 `text` 与 `tokens`
都来自它。不打开 `metal` 时仍是 `UnlinkedDecoder`，空串、`is_final` 为真。

- 空音频：`Session::finish` 在样本为 0 时直接回空串定稿，`finish` 返回 0。
- 打不开权重或某一步失败：文本为空串，原因 `定稿计算失败：<错误>` 进 `failure_reason`，
  `voice_session_finish` 返回非 0。
- 部分文本（说话中）目前不发：`WeightDecoder` 只在 `is_final` 时算，非定稿步回空串。

## 一行 JSON 与失败原因

回复口有两个：C 函数指针 `voice_text_fn`（旧）与一行 JSON 的 `voice_reply_fn`（`voice_engine_set_reply_sink`）。JSON 行由 `voice-ffi/src/json_line.rs` 拼出，键就是 Swift 侧 `RecognitionReplyParser` 读的六个：`session`、`text`、`decoded`、`kind`、`ok`、`message`。两处回复因此同形，解析器只有一处。

- JSON 口装上之后文本事件只走它，文本指针不再被调用（两个口不会重复发）。
- `decoded` 恒为真：这条回复带着一段解出来的文本。部分结果只在文本变化时才发，定稿不看这一位。
- 定稿失败时先发一条空串的 `kind:"final"`（会话确实没有文本），再发一行 `ok:false`、`message` 是原因。
- 原因同时留在 `last_error` 里，`voice_engine_last_error(engine, buf, n)` 同步读出；调用线程据此把原因写进日志，不必等回调。

## 容差口径与归因闸（2026-11-14，见 notes/060）

容差只在 `code/voice-engine/voice-parity/src/tolerance.rs` 定义一处：
`容差 = 参考张量的绝对值上界 × 2^-11 × 允许的单位数`。参考是 f16，`2^-11` 是
「元素按自身量级折算的半个 f16 间距」的上界；单位数与实测值写在每个常量旁边。
编码器、解码器与梅尔三条闸都引用它，不再各写绝对容差。

解码器主闸（`decoder_parity::decoder_prefill_matches_reference`）带两条归因断言：
`RopeMode::SinOnly` 与 `qk_norm: false` 都必须让首 64 维最大差变大，并且大到容差外。
本次没有改算术：解码器主闸实测差仍是 7.8125e-2（容差 8.203125e-2，余量 1.05 倍），
编码器三条与端到端四条不变；`cargo test --workspace --offline` 49 通过、4 忽略、0 失败。

## 梅尔前端换 vDSP 实数 FFT（2026-11-14，见 notes/062）

`voice-mel` 不再每帧对 201 个频点各做一次 400 点复 DFT。macOS 上走 Accelerate 的
`vDSP_DFT_zrop`：400 = 5 × 80，五条 80 点实数 DFT（80 = 5·2⁴ 是 vDSP 支持的长度）
再按 `X[k] = Σ_r W_400^{rk}·A_r[k mod 80]` 合并。400 本身 vDSP 没有实现
（`vDSP_DFT_zrop_CreateSetup(400)` 返回空指针），也不补零到 512 / 480——见 notes/062 第 1 节。
非 macOS 目标退化成逐点直接 DFT，那条路径不追求速度。

`voice-mel` 因此多了一条链接要求：`#[link(name = "Accelerate", kind = "framework")]`。
`cargo test -p voice-mel` 由 rustc 自己加上这条参数；链 `libvoice_ffi.a` 的临时程序与
Squirrel 本来就带 `-framework Accelerate`（见上文 otool 那一节与 `link.sh`），不必再加。

## 说话中出字：每满 2 秒回一条 `partial`（2026-11-14，见 notes/063）

`voice-mlx` 新增 `src/backend/stream.rs`：`Stream` 带这一次按住的样本、已结束各窗的
投影输出（`prefix`）、已进前缀的帧数与上一段的整段假设；`Engine::stream_step` 跑一步：
整段重算梅尔 → 满 800 帧的窗冻结进前缀 → 活动窗重编 → 提示 = 模板 + 已固定的文本，
只重算未固定的 5 个 token。`prefix` 与已固定的文本跨步复用；解码器的键值只在步内复用
（音频占位个数每步都变，`<pad>` 之后的 RoPE 位置整体平移，跨步对不上）。

窗边界与一次性编码那条路是同一条算术，但不是逐位相同：1200 帧一次编完与切成
800 + 400 两段编，投影最大绝对差 1.0691956e-4（f16 归约次序）。8 秒以内两条路是
同一次调用、同一个张量，逐位相同，所以 2 秒、4 秒、8 秒的定稿与改造前一字不差。

`voice-ffi/src/decoder.rs` 的 `WeightDecoder` 分两条：非定稿步走
`stream_step_on_resident`，定稿仍走原来那条整段重算。`json_line.rs` 与 `SessionSink`
一个字没改：`kind:"partial"`、`decoded` 恒为真本来就在。

## 提示头与已结束窗的行只预填充一次（2026-11-15，见 notes/069）

说话中那条路（`voice-mlx/src/backend/stream.rs`）每步要预填充的不再是整条提示：
`Stream` 留一份 28 层的键值缓存，缓存开头「提示头 + 已结束各窗的行」只在第一次算一遍。
位置 `0..head_tokens + prefix.len()/HIDDEN` 的内容每步一样，后面每步截掉重算——
音频占位个数每步变、位置整体平移，所以能照用的只有仍然**是前缀**的那一段。

截断与续写都按绝对位置对齐，拼一次 `concatenate` 就够（`kv_write` 本来就做这件事），
后端没有新增「两段键值」的形状。新冻窗那一步（活动窗刚凑满 800 帧）要整窗重算一次：
那 104 行在缓存里还是按活动窗编出来的旧内容。

TextDecoder::prefill_chunk(ops, cache, tokens, audio, position, head_dims, options)
TextDecoder::greedy_from_cache(ops, cache, base, next, max_new_tokens, options)
transcribe::{PromptParts, prompt_parts, splice_prompt}   // head / pads / tail 三段按 id 拼
