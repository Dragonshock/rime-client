# 028-derivation-type4me-seam：Type4Me 与现有语音端口的对应

本文只回答一件事：`027` 已核对的 Type4Me 机制，怎样对应 `007` 的识别流、改写流和交付。用户希望把它接进来、从而少写一层。少写不是取舍依据。对得上的端口可以复用契约；对不上的端口不因为仓库已经有一套上屏就换掉。倾向全部是候选。

## 1. 推理

`027` 把 Type4Me 拆成三截，三截的输入类型不同。

- 识别截把 16 kHz PCM16 送给本机 MLX 的 Qwen3-ASR，热词是一段 `context`。流式预览另走 sherpa-onnx SenseVoice，定稿可以盖住部分结果。这和原语 4 的「帧进、文本假设出」同向，但返回值仍是整段文本或 `authoritativeText`，没有修订指针。
- 改写截把已经得到的文本和提示词送给 `LLMClient` 或本机 `llama.cpp`。输出是一段字符串。原语 5 还要「不替换」。Type4Me 没有这个种类。
- 交付截把最终字符串放进剪贴板并发送 Command-V。原语 8 的交付吃的是预编辑或提交意图。`027` 没有 `setMarkedText`。

把三截当成一个「语音输入」函数接进来，会把上屏通道一起焊上。那是 `007` 已经舍弃的总函数焊法。候选是只接契约相同的那一截。

## 2. 候选对应

| 原语 | Type4Me 里已有的契约 | 对不上的部分 |
| --- | --- | --- |
| 识别流 | `SpeechRecognizer.sendAudio` / PCM 缓冲；Qwen3 WebSocket 的 PCM16-LE、16 kHz；`transcribe(..., context=)` | 无会话标识，无「修订哪一条」；热词不是五槽 |
| 改写流 | `LLMClient.process` 的文本与提示词；流式增量回调 | 返回值只有字符串；本机实现不是 mlx-lm |
| 交付 | `TextInjectionEngine.inject` | 剪贴板与 Command-V，不是预编辑事务 |

候选倾向：

1. 说话过程中的识别，沿用 Type4Me 已经在用的那条 MLX 契约：PCM16、16 kHz、热词字符串、部分文本与定稿文本。调用点可以是他们的 WebSocket `/ws`，也可以是 `024` 已测的 `feed_audio`。两条都产出整段或片段文本，修订指针仍由调用方在外面算，和 `021` 的候选相同。SenseVoice 部分结果是另一件制品。`027` 没有本机同时驻留两者的内存数，本篇不选「必须两级」。
2. 改写仍是 `025` 的候选：有字符串就由适配器与原文比较，相同则不替换。Type4Me 的 `LLMClient` 可以当远程绑定的一种调用形状。它不证明替换更正确，也不把 llama.cpp 写成 mlx-lm。
3. 交付不调用 `inject`。我们的宿主字段写入仍是预编辑与提交。Command-V 会把字交给当前前台应用的粘贴，不区分键盘输入法正在组合的那一段。要改用这条上屏，是另一条交付绑定，不是识别绑定的附带结果。

舍弃的接法：把 Type4Me 可执行文件当作输入法进程，或用 `type4me://toggle` 当作端口。URL 只开关它自己的录音，转写不回到调用方。`Package.swift` 也没有识别产品可以链接。

## 3. 少写的是哪一层

少写的是识别服务里已经写好的 PCM 封包、2 秒部分转写、静音不把热词念出来、以及热词字符串的位置。这些在 `server.py` 里。交付、会话标识、修订指针、另外四槽、以及「替换是否更正确」，Type4Me 没有替现有端口做完。把上屏改成粘贴，少写的是 IMK 事务，换来的是剪贴板占用和合成按键。那一换不在本篇的候选里。
