# 030-derivation-type4me-voice-implementation：按识别与改写顺序实现，交付停在 inject 之前

本文只做一件事：把 Type4Me 热键链上已经排好的「部分文本，再定稿，再对定稿全文改写」收成 Rime 客户端语音接口的模块、输入输出、会话状态和两种适配器记录。交付停在写出预编辑或提交记录，不调用 `TextInjectionEngine.inject`。文中的模块、记录、迁移与倾向都是候选。

仓库是 `dev-docs/refs/code/type4me`，提交 `28353340207c5288f9dcaf2e71928cc3487d49cf`。`027` 核对了识别函数与 `inject` 的函数体，`028` 写了契约对应，`029` 追了从快捷键到 `inject` 的调用点。本文不重开函数体，不把剪贴板路径写成交付，也不改 librime 的键盘路径。

用户要求的是：这个 Rime 输入法客户端提供一个接口用来接入语音输入；功能机制参考 Type4Me。`007` 的原语 4、原语 5、原语 7、原语 8 仍是对外类型。`025` 的改写比较仍在适配器里。`013` 里「未取走的键盘事件仍进键盘链」这一句，本文沿用。

## 1. 推理链

### 1.1 为什么是识别，然后才改写

`029` 记下的热键链把数据分成先后三截，三截的输入类型不同。

1. 录音过程中，`SenseVoiceASRClient.updatePartial` 与 `confirmSegment` 交出转写。`isFinal` 为假，`authoritativeText` 为空。展示用已确认片段拼上 `partialText`。消费者是 `handleASREvent` 和悬浮条。这一截不调用 `LLMClient.process`，也不调用 `inject`。
2. 停止之后，`endAudio` 用累积的整段 PCM 做一次定稿。Qwen3 有字则整段替换已确认片段，再 `emitTranscript(isFinal: true)`。会话把 `currentTranscript.displayText` 收成 `effectiveText`。它还不是 `inject` 的参数。电平从未越过说话阈值，或定稿是空字符串时，`finishTextOutput` 不往下走。
3. `finishTextOutput` 收到的是这段字符串。提示非空时才 `client.process(text:prompt:...)`（`RecognitionSession.swift` 里该调用位于定稿已经取出之后）。输入是文本，不是 PCM。快速模式的提示是空字符串，这一截不调用。

改写若插进第 1 截，它吃到的就还是采样帧或未定稿片段。`007` 原语 5 的输入是已经是文本的假设。Type4Me 自己也把 `process` 放在定稿全文之后。本文按这个顺序实现：识别适配器先交出部分文本，停止后再交出定稿文本；改写适配器只接收定稿全文。

`028` 写明热键链上的部分文本来自 sherpa-onnx，定稿可以来自 `POST /transcribe`。`SenseVoiceWSClient` 没有构造点，`/ws` 的部分 JSON 不进入 `handleASREvent`。`025` 写一次会话只接一行识别候选和一行改写候选，不把两行串成前后两级。本文沿用：部分文本与定稿文本是同一条识别记录上的两种种类，不是两级制品焊死。哪一行制品填这一条记录，见缺口，不在本文挑。

### 1.2 为什么交付停在 inject 之前

同一函数在改写返回之后才上屏。`onASREvent?(.willInject)` 与 `state = .injecting` 在 `RecognitionSession.swift:2580` 一带，真正的调用是其后的 `injectTracked`（`2700`）或 `inject`（`2709`）。`027` 读过 `inject` 的函数体：它不接收输入法的预编辑。外部应用在前台时，那条路径占用剪贴板并合成按键。`028` 因此不把 `inject` 当作识别契约的附带结果。

Rime 客户端的宿主字段要的是预编辑或提交。`007` 原语 7 的意图只有会话标识、范围、字符串、种类。原语 8 的交付吃的是这条意图，不是 `InjectionOutcome`。若把 `inject` 接进来，识别绑定会连上屏通道一起换掉，回到 `007` 已经舍弃的总函数焊法。

本文的交付物就是这条记录，种类只取预编辑或提交。组合在记录写出后返回。不调用 `TextInjectionEngine.inject`，不调用 `injectTracked`，不进入 `.injecting`。将要交给 `inject` 的那个字符串，改记成提交记录里的字符串；差异不上屏时，字符串改回识别定稿。

Type4Me 的部分文本停在悬浮条，不写宿主字段。本文把同一截「尚未进入 inject」的文本映成预编辑记录，因为接口的宿主是输入法字段，不是菜单栏悬浮条。这是呈现的候选映射，不是把 `RecognitionTranscript` 当成端口。

### 1.3 为什么相同不替换，没有分数不上屏

`LLMClient.process` 的返回值是一段字符串，没有「不替换」这一种类（`027`、`028`）。`025` 把比较放在适配器：全文相同则不替换。比较材料是送进去的定稿全文和返回的全文，不是公共前缀，也不是 Type4Me 没有的修订指针。

`023` 与 `025` 没有这样一对数字：某一仓库路径、某一次 MLX 量化、替换文本的错误少于识别假设。没有这个纠错分数时，两段字符串不同只说明它们不同，不说明替换更正确。候选是：全文不同仍写入改写记录，供核对；呈现不把返回串放进预编辑记录或提交记录。上屏字符串保持定稿原文。

这不是把改写角色留空。适配器仍然接收定稿全文，记录里仍然能读出原文。只是交付记录的字符串不取那份差异。

### 1.4 为什么未取走的键仍进键盘链

`007` 原语 2：被触发取走的键盘事件不进入键盘组合；未被取走的事件原样进入。取走只产生打开或关闭，不写字段。`008` 曾写自有预编辑还在时把未取走事件停在链外。`013` 不采用那一句，因为原语要求未取走事件原样进入，链内不再出现第二套分支。

本文沿用 `013`。未取走的事件仍进键盘链。Squirrel 现行 `handle` 在译码之后调用 `rimeAPI.process_key`（`dev-docs/refs/code/squirrel/sources/SquirrelInputController.swift:412`）。语音文本不编码成按键，不插在这次调用前面，librime 里的键盘路径不改。

### 1.5 舍弃的接法

- 舍弃把 Type4Me 可执行文件或 `type4me://toggle` 当作端口。`028`：该 URL 只开关它自己的录音，转写不回到调用方。`Package.swift` 没有可链接的识别产品。
- 舍弃用 `inject` 的剪贴板与合成按键充当交付。交付记录的种类只有预编辑与提交。
- 舍弃在部分文本上调用改写。改写的输入到定稿全文才成立。
- 舍弃没有 MLX 纠错分数时把全文差异上屏。
- 舍弃改 librime 键盘路径，或把未取走事件拦在键盘链之外。
- 舍弃把 SenseVoice 与 Qwen3 串成前后两级。`025` 不串行，`028` 也不把两级写成同一条识别记录的前提。

## 2. 模块与输入输出

下面的模块是候选。它们是同一次组合里的分工，不是总函数，也不是各自一个进程。`007` 允许同一进程顺序履行多条原语。顺序就是第 1 节的三截，停在交付记录。

| 模块 | 输入 | 输出 | 碰不到 |
| --- | --- | --- | --- |
| 采集 | 会话开闭；设备与使用权是否成立 | 有序帧，或无帧并结束 | 热词、识别文本、宿主字段 |
| 识别适配器 | 有序帧、热词字符串、会话标识 | 识别记录：部分文本或定稿文本 | 改写返回值、交付记录、`inject` |
| 会话 | 打开时的字段标识与范围；此后的识别记录与改写记录 | 第 3 节的状态 | 键盘组合状态；另一枚会话的范围 |
| 改写适配器 | 定稿全文、会话标识；提示缺席则不调用模型 | 改写记录 | PCM、宿主字段、`inject` |
| 呈现 | 识别记录、改写记录、会话是否仍允许交付 | 零条或多条交付记录 | 采样帧、`inject` |
| 键盘入口 | 一枚键盘事件 | 取走则只产生开闭；未取走则原样进入既有键盘链 | `process_key` 之后的路径 |

帧的候选形状跟 Type4Me 已经送进识别的格式对齐，格式写在帧上，不由「现在加载了哪个模型」隐含：

| 字段 | 取值 |
| --- | --- |
| 编码 | PCM16，小端 |
| 采样率 | 16000 |
| 声道 | 1 |

`AudioCaptureEngine` 把 `sampleRate` 写成 16000，`targetFormat` 是 `pcmFormatInt16`、16000、单声道（`AudioCaptureEngine.swift:23-33`）。`server.py` 把 `SAMPLE_RATE` 写成 16000，`BYTES_PER_SAMPLE` 写成 2，注释写 PCM16-LE（`server.py:87-90`）。采集不输出字。使用权不成立时无帧并结束，不把这件事报成一段识别成功。

热词不进帧。`server.py` 把热词文件按行读出，用空格拼成进程级 `_hotword_context`，再传给 `transcribe(..., context=)`（`server.py:385-391`、`225`）。识别适配器的热词输入因此是这一段字符串。`025` 写五槽里另外四槽没有落在已读形参上。本文不新写拼接，不把缺席改成空字符串。

## 3. 会话状态

候选。寿命与两位标记分开，因为 Type4Me 的关闭信号（热键 `onStop`）先停采集、再取定稿，改写与上屏都在那之后。关闭本身不写字段。`013` 去掉了「提交成功随即关闭」和「同一字段至多一枚允许交付」。本文不把这两句写回来。

打开成功时写入：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与键盘引擎的 `RimeSessionId` 不是同一枚。识别记录、改写记录、交付记录都带它 |
| 字段快照 | 打开时记下的宿主字段标识。交付时与当前要写的那一份比较。平台值仍未知 |
| 范围快照 | 打开时的范围。可以是空选区 |
| 寿命 | 未建立、开放、已关闭 |
| 收束已请求 | 是或否。已请求只说明触发不再把这次当作未收束 |
| 交付许可 | 允许或拒绝 |
| 自有预编辑区间 | 无，或会话自己登记的一段范围 |
| 识别记录 | 空、一条部分文本，或一条定稿文本。新的部分文本整段替换上一条部分文本 |
| 改写记录 | 未到、不替换，或全文不同 |

未列出的输入不迁移。

| 当前 | 输入 | 迁到 | 字段 |
| --- | --- | --- | --- |
| 未建立 | 触发打开，且当时能记下字段标识与范围 | 开放，允许交付，收束未请求 | 不动 |
| 未建立 | 打开时字段标识记不下来 | 保持未建立 | 不动 |
| 开放，允许交付 | 部分文本记录，且标识相同 | 仍开放 | 识别记录换成这一条。呈现可另写预编辑记录。不写提交记录 |
| 开放，允许交付 | 定稿文本记录，且标识相同 | 仍开放 | 识别记录换成定稿。改写记录仍是未到。不写提交记录 |
| 开放，允许交付 | 触发给出关闭 | 仍开放，允许交付，收束已请求 | 不动。关闭不调用改写，也不写字段 |
| 开放，收束已请求，识别记录已是定稿 | 改写记录到达，且标识相同 | 仍开放 | 改写记录写入。呈现这时才可写提交记录 |
| 开放，允许交付 | 预编辑记录被宿主应用 | 仍开放；自有区间换成该范围 | 只有该区间的预编辑被替换 |
| 开放，允许交付 | 提交记录被宿主应用 | 仍开放；自有区间变为无 | 该范围成为提交文本。不调用 `inject`。不因这一笔进入已关闭 |
| 开放 | 字段标识偏离快照 | 仍开放，拒绝交付 | 不动。识别与改写可以继续留在记录里 |
| 开放，收束已请求 | 呈现不再持有未发出的记录，且自有区间为无 | 已关闭 | 不动 |
| 已关闭 | 迟到的识别、改写或交付记录 | 保持已关闭 | 不动 |

标识不同的记录不进入上表，当前会话的各位不变，字段不动。`029` 的 `handleASREvent` 先核对 `sessionGeneration`，对不上就不写入 `currentTranscript`。本文的会话标识担任同一件事：迟到结果停在会话记录之外，不改字段。

同一字段上可以有另一枚仍允许交付的会话。范围在宿主上对不上时，该条交付记录整笔拒绝。这是逐条拒绝，不是打开时只留一枚。

失焦不是会话标识。触发不把它当成关闭，并且字段标识也未偏离快照时，上表不迁移。

核对：部分文本到达时，提交记录是否尚未写出，`inject` 是否未被调用？定稿已写入识别记录、改写记录仍是未到时，提交记录是否仍未写出？

## 4. 识别适配器的记录

对外记录是候选。下面的源码只说明 Type4Me 把部分与定稿放在同一结构里，不把这个结构当成端口。

```swift
// 源：dev-docs/refs/code/type4me/Sources/Type4Me/ASR/SpeechRecognizer.swift:48-53
struct RecognitionTranscript {
    let confirmedSegments: [String]
    let partialText: String
    let authoritativeText: String
    let isFinal: Bool
}
```

`isFinal` 为假时，`emitTranscript` 把 `authoritativeText` 写成空字符串（`SenseVoiceASRClient.swift:598-608`）。`displayText` 在权威文本为空时退回片段与部分文本的拼接（`SpeechRecognizer.swift:76-77`）。定稿时权威文本等于当时的拼接；Qwen3 成功则已确认片段只剩校准后的一整段。

适配器向外只交下面这一条。`confirmedSegments` 不出现在记录里。调用方看见的是当时的一整段文本，种类标明它是部分还是定稿。

| 字段 | 部分文本 | 定稿文本 |
| --- | --- | --- |
| 种类 | 部分 | 定稿 |
| 文本 | 当时要展示的整段 | 定稿全文 |
| 会话标识 | 有 | 有 |

输入侧再记三样，都不放进这条输出：PCM16、16000、单声道的有序帧；热词字符串；会话标识。热词字符串对应该进程的 `context`，不是五槽对象。

新的部分文本替换会话里的上一条部分文本。替换留在会话内，不因此写出提交记录。返回值里没有「修订的是哪一条」。`021` 已写三份 MLX 入口都没有修订指针，本文不补一个字段来冒充。

空定稿是正常输出。`server.py` 在样本短于 0.3 秒或近乎静音时返回空字符串。空定稿不写交付记录，与 `029` 里空 `effectiveText` 不调用 `inject` 同一方向。

## 5. 改写适配器的记录

输入是定稿全文与会话标识。不是部分文本，不是 PCM。提示缺席时不调用模型，记录直接为不替换，原文留下。Type4Me 快速模式就是提示为空则不调用 `process`（`029`）。调用失败或返回空字符串，同样记为不替换。Type4Me 在失败时把待写字符串退回识别定稿，然后仍可能进入 `inject`。本文退回原文，但只写入改写记录和其后的交付记录。

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与定稿那条相同才接受 |
| 原文 | 送进去的定稿全文 |
| 返回串 | 模型返回的字符串。未调用、失败或空结果时缺席 |
| 判定 | 不替换，或全文不同 |

判定只做全文比较：

- 返回串缺席，或与原文逐字相同：判定为不替换。
- 返回串与原文逐字不同：判定为全文不同。

没有 MLX 纠错分数时，判定为全文不同也不把返回串写进交付记录。呈现使用原文。分数这一格目前是空的：`025` 不从两张口径不同的 CER 表里挑权重，也没有 MLX 量化上「低于识别假设」的一对数字。空着就不取返回串上屏。本文不补阈值。

「不替换」和「全文不同但不上屏」对交付记录的字符串效果相同，都是原文。改写记录里二者仍然分开，用来核对比较做过没有。

## 6. 交付记录

一条交付记录只含四字段：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与会话记录相同才可以应用 |
| 范围 | 见下 |
| 字符串 | 部分文本，或定稿原文。没有 MLX 纠错分数时不取返回串 |
| 种类 | 预编辑，或提交 |

记录上没有采样帧，没有制品名字，没有键盘事件，没有 `InjectionOutcome`。

范围沿用 `013` 的候选，本文不重新解释：

- 种类为预编辑，且尚无自有区间：范围等于打开时的范围快照。应用之后把写下的那段记为自有区间。
- 种类为预编辑，且已有自有区间：范围等于该区间。提交文本不增加。
- 种类为提交，且已有自有区间：范围等于该区间。应用后区间登记变为无。字段上不留下预编辑副本再加一段提交。
- 种类为提交，且无自有区间：范围等于打开时的范围快照。

呈现的候选顺序，对齐第 1 节，并在 `inject` 的位置停住：

1. 每条部分文本至多一条预编辑记录，字符串是该部分文本。零条提交记录。
2. 定稿写入识别记录、改写仍未到：不写提交记录。候选是再写一条预编辑记录，字符串换成定稿全文，替换自有区间。Type4Me 在这一步用权威文本换掉片段，发生在 `inject` 之前。
3. 改写判定为不替换，或全文不同但没有纠错分数：一条提交记录，字符串是定稿原文。
4. 写出上述记录后返回。不调用 `inject`，不调用 `injectTracked`。

应用这条记录的是宿主字段上的预编辑写入或提交写入。Squirrel 里能看见的名字是 `show(preedit:selRange:caretPos:)` 与 `commit(string:)`（`SquirrelInputController.swift:522` 一带与 `586`）。`013` 写过：若复用这两个函数，会碰到控制器上那份键盘预编辑缓存。那是距离。本文不把这次复用写成已经接好的通道，也不改用 `inject` 去绕开。记录的种类仍然只是预编辑或提交。

会话判定为拒绝交付时，不写字段，包括不先写一段临时文本。标识不一致或寿命已关闭时同样不写。

## 7. 键盘事件

键盘入口对一枚事件只有两个结果。

- 取走。事件不进入键盘链。只用于某一会话的打开或关闭。不写字段，不携带识别文本。
- 未取走。类型与修饰保持原样，进入键盘链。链上仍是译码、`process_key`、键盘自己的预编辑与提交。不因语音会话增加分支。

自有预编辑区间还在时，未取走的事件也进入键盘链。此后两段预编辑在字段上各变成什么，`013` 记为未知，本文不补成「先停住再进入」。语音交付若无法把记录里的范围对应到自己登记的区间，整笔拒绝。拒绝不改键盘链。

语音路径不向键盘链提交采样帧、识别记录、改写记录或交付记录，也不读取键盘组合来判断语音进行到哪一步。

## 8. 当前倾向（候选）

候选倾向如下。

语音接口按 Type4Me 热键链的数据顺序实现。采集交出 PCM16、16000、单声道的有序帧。识别适配器吃这些帧和一段热词字符串，先交出部分文本，停止后再交出定稿文本。改写适配器只吃定稿全文；与返回串逐字相同则记录为不替换。没有 MLX 纠错分数时，全文不同只留在改写记录里，不上屏。呈现把部分文本排成预编辑记录，在改写记录到达后排成一条提交记录，字符串取定稿原文。这些记录就是交付。组合在记录写出后返回，不调用 `TextInjectionEngine.inject`。未取走的键盘事件仍进键盘链。librime 的 `process_key` 路径不改。

反论：Type4Me 在改写之后立刻进入 `inject`，松开时前台应用里可以已经有字。本文改成提交记录，字要等宿主应用该记录才进入文档。应用若排在改写返回之后，中间字段上只有预编辑。`007` 已记下有的宿主在说话结束时期望文档里已经有字。目标宿主在定稿之后还留不留得住预编辑，仍未测量。因此「先预编辑、改写记录到达后再一条提交」保持候选。即便呈现改成收束时先提交原文，记录种类仍然只是预编辑或提交，仍然不调用 `inject`。

另一反论：未取走的键在预编辑还在时进入未改过的键盘链，键盘路径可能写下它自己的预编辑或提交，语音登记的区间随后对不上。`013` 接受这一后果，不把事件停在链外。本文同样接受。对不上的交付记录整笔拒绝，假设留在会话里。

## 9. 缺口

下列各项缺证据。本文不补成一种选择。

1. 识别记录这一行接 `POST /transcribe`、`024` 已测的 `feed_audio`，还是别的整段入口：`028` 写它们都产出文本。本文不挑。`/ws` 不在 `029` 的热键链上。
2. 不用 SenseVoice 时，定稿之前有没有另一段部分文本：未知。没有部分文本时，呈现可以只有定稿之后的预编辑记录。不补一段假的部分文本。
3. 点名仓库路径、并且在 MLX 上低于识别假设的纠错分数：仍无。因此全文不同不上屏。
4. `host_app`、`field_role`、`cursor_before`、`corrections` 进入热词字符串或改写提示的拼法：未知。不补模板。
5. 宿主应用预编辑记录与提交记录时，会不会改写键盘预编辑缓存：`013` 记为距离。本文不把 `show` / `commit` 收成已经接好的通道。
6. 自有预编辑仍在、未取走键已经进入键盘链之后，两段文本如何同时留在字段上：未知。
