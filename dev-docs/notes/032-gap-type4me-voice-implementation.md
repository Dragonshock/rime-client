热键链上已经写明的，不是这条未知。部分文本来自 `SenseVoiceASRClient.updatePartial`。停止后的定稿可以来自 `POST /transcribe`，响应是一段文本，没有部分字段。`server.py` 的 `/ws` 会发送 `is_final` 为假或真的 JSON；`SenseVoiceWSClient` 没有构造点，会话不订阅，`031` 不把它当作这条记录的部分文本。别的客户端各自有没有部分文本，写在各自的发出函数上，不代替未点名的那一行。

**存在依据：** 用户要求功能机制参考 Type4Me，同时接口通用，不把某一家内部结构焊进端口。原语 4 的输出是会话内的假设，不是提交文本。原语 9：重新配对不改变识别流的输入输出；对不上的契约不成立时，角色空着。`030` §1.1 与 §9 第 1、2 点不把 SenseVoice 与 Qwen3 串成前后两级，也不挑哪一行填记录。`031` 决定 2 与决定 3 沿用，并写明没有部分文本时不补一段假文本。

**现在是否需要补证：** 不需要把热键链再走一遍，也不需要调用 REA。上面的报文和调用点已经在源码里。记录的种类、文本、会话标识，在入口未点名时仍然是这三个字段，不为此再点名一行。若要写「这一行在定稿前交出部分文本」，需要点名那一行，并在它自己的返回里读到定稿之前的那段文本。读不到时，呈现可以只有定稿之后的预编辑意图。

## 2. 四槽进入热词字符串或改写提示的拼法，仍然没有槽位表

**未知：** `host_app`、`field_role`、`cursor_before`、`corrections` 用什么名字、什么分隔，进入识别用的热词字符串，或进入改写提示。Type4Me 已经展开的占位符不是这四槽。

```swift
// 来源: dev-docs/refs/code/type4me/Sources/Type4Me/LLM/PromptContext.swift:23-24，提交 2835334
struct PromptContext: Sendable {
    let selectedText: String
    let clipboardText: String
}
```

`expandContextVariables` 替换 `{selected}`、`{clipboard}`、`{tools_json}`。`LLMPreparedPrompt` 另有 `{text}`，以及 `<selected>`、`<clipboard>` 数据块。热词在 `server.py` 里按行读出，用空格拼成 `_hotword_context`，再传给 `transcribe(..., context=)`。这段拼接只有热词。四槽的名字不在这两处。选中文本也不是光标前文。

**存在依据：** 原语 6：槽位是名字到文本的映射，不是某一个模型的提示词格式；来源读不到时槽位缺席，快照仍然成立。用户要求接口通用。`011` 把一次汇集写成 `host_app`、`field_role`、`cursor_before`、`hotwords`、`corrections`。`026` 第 2 条记下已读 MLX 入口没有这张表。`030` §9 第 4 点与 `031` 决定 8 不把另外四槽拼进热词字符串或改写提示，也不把缺席写成空字符串。

**现在是否需要补证：** 不需要在同一份 `PromptContext` 里再找这四个名字。不把 `{selected}` 或剪贴板文本改名成 `cursor_before`。不新写分隔符。空格拼接只覆盖 `hotwords`。四槽缺席时，识别仍可接受热词字符串缺席，改写仍可在提示缺席时记为不替换。个人词、纠错对与键盘路径上的用户词是不是同一存储，原语 6 不规定，本文不另开一条。

## 3. 点名仓库路径的 MLX 量化，仍然没有「替换文本错误更少」

**未知：** 哪一个仓库路径、哪一次 MLX 量化、在哪一个测试集上，替换文本的错误少于同一次的识别假设。没有这一对时，全文不同只说明两段字符串不同。

**存在依据：** 原语 5：输出是「不替换」或「替换为这段文本」；「不替换」是正常输出。用户要求按 Type4Me 的机制把语音输入做到可接入。Type4Me 的 `LLMClient.process` 返回的是字符串，返回值里没有「错误更少」。`023`、`025` 与 `026` 第 3 条没有交出点名路径上的那一对数字。`030` §1.3 与 `031` 决定 5 因此不把返回串写入预编辑意图或提交意图。

**现在是否需要补证：** 不需要再读 `process` 的函数体来寻找分数，也不需要调用 REA。不把别的口径的 CER 表借来充当这一对。需要补的是：某一个点名仓库路径、某一次 MLX 量化、某一个测试集上，替换文本的错误少于识别假设。没有这一对时，不补阈值；意图里的字符串保持定稿原文。恒等「不替换」仍然对得上原语 5 的核对句。

## 4. 输入法字段上，预编辑与未取走的键相遇之后变成什么，仍未观察

**未知：** 语音侧自有预编辑已经在宿主字段上时，一枚未取走的键盘事件进入键盘链之后，这段预编辑与键盘路径自己的预编辑或提交各变成什么。同一处没有宿主观察的还有两句：定稿之后、提交意图应用之前，预编辑是否还留在字段上；对同一范围连续两次提交、且第二次字符串不同时，文档历史上留下几段。

`show(preedit:selRange:caretPos:)` 把控制器上的 `preedit` 设为参数并调用 `setMarkedText`。`commit(string:)` 调用 `insertText` 后把 `preedit` 置空（`SquirrelInputController.swift` 的 `commit` 与 `show`）。这只说明复用这两个函数会改写键盘预编辑缓存，不是已经接上的语音通道。本文不把这次复用写成交付。

**存在依据：** 用户要求接口做在这个 Rime 输入法客户端上。原语 2：未被取走的键盘事件原样进入键盘组合。原语 7：先一直预编辑、到改写结束再提交一次，是一种配对，不是不变量；两种意图序列都能满足原语 7。原语 8：交付的输入是意图；键盘组合不读取意图；另一条通道的做法，本原语不给定。`012` 第 1、2 条记下这两件宿主事实未测量。`026` 那一轮不重开它们。`030` §8、§9 第 5、6 点与 `031` 仍然未知的第 5 至 7 点把它们留在本实施方案里，因为交付停在预编辑或提交意图，不调用 `inject`。

**现在是否需要补证：** 不需要用 Type4Me 的 inject 来回答输入法字段。那条上屏不写成交付。不需要改 librime 的 `process_key`，也不需要调用 REA。需要的是宿主观察：预编辑已经在字段上时，一枚普通键进入现行键盘链之后，预编辑文本与提交文本各变成什么；收束之后、下一次写入之前，预编辑是否仍在。没有这些观察时，不把「先预编辑、再一条提交」写成原语 7 的不变量，也不把未取走的事件停在键盘链之外。对不上自有区间的意图整笔拒绝。
