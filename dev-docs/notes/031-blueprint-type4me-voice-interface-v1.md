# 031-blueprint-type4me-voice-interface-v1：Type4Me 顺序下的语音接口开发参照

本文把 `007`、`028`、`029`、`030` 收成一份开发参照，供调用方按记录实现适配器。划分、记录、迁移与配对都是候选。交给本文的异议清单是空的：没有条目被吸收进正文，也没有条目被改写成另一种倾向。`030` 已经留下的未知继续留在文末，这里不补成选择。

用户要求 Rime 输入法客户端提供一个接入语音输入的接口，功能机制参考 Type4Me。参照的仓库是 `dev-docs/refs/code/type4me`，提交 `28353340207c5288f9dcaf2e71928cc3487d49cf`。`029` 已追完快捷键到 `inject` 的调用点，`030` 已把交付停在该调用之前。源码写明的机制，本文直接沿用，本次没有调用 REA。

下文 `007` 指 `dev-docs/notes/007-derivation-voice-input-primitives.md`，`028`、`029`、`030` 指同目录下同号笔记。原语编号指 `007` §3。

## 架构

### 一次会话上的组合，不是总函数

`007` §1 把语音优化输入拆成四件先后不同的事：采样帧还不是字；识别假设可以被更晚的假设修订，所以还不是宿主文档上的提交；在上下文上决定保留还是换成另一段文本；文本进入宿主字段时，预编辑可被替换，提交进入宿主文档。`007` §2.2 舍弃把这四件事焊成 `优化(采样) → 提交文本`。`028` §1 把 Type4Me 的识别截、改写截、交付截看成三截不同的输入类型，并写明整段接进来会把上屏通道一起焊上。

本参照的架构是：在一枚语音会话上组合这些原语，组合顺序取 `029` 记下的热键链数据顺序，停在 `030` 的交付记录。没有第十个「语音输入」对象把各截收成一个函数。Type4Me 可执行文件与 `type4me://toggle` 不是这个架构里的端口。`028` §2：该 URL 只开关它自己的录音，转写不回到调用方；`Package.swift` 没有可链接的识别产品。

候选的数据依赖如下。它是组合顺序，不是一个函数的步骤表。

1. 触发只发出打开或关闭。输出里没有采样帧，也没有文本。
2. 会话在打开成功时记下标识、宿主字段标识的快照、范围快照，以及允许交付。
3. 上下文只读汇集一份槽位快照。识别适配器拿到的不是这份快照本身，而是其中热词槽投影出的一段字符串，或该字符串缺席。
4. 采集交出有序帧，或无帧并结束。帧上带格式，帧上没有字。
5. 识别适配器先交出部分文本，停止后再交出定稿文本。两条都是同一条识别记录上的种类。假设的替换留在会话内。
6. 部分文本可以排成预编辑意图。这一截不调用改写适配器。
7. 触发给出关闭之后，会话仍开放。关闭本身不写字段。定稿进入识别记录之后，改写适配器才接收定稿全文。
8. 呈现在改写记录到达之后排成提交意图。字符串取定稿原文。
9. 交付对一条意图整笔应用，或整笔拒绝。拒绝时字段与应用前逐字相同。组合在意图写出并按此规则应用或拒绝之后返回。

采集不读取改写结果。识别适配器不选择交付通道。改写适配器不读取键盘组合，不持有宿主字段。呈现不发明一段优化文本。交付的输入里没有采样帧，也没有制品名字。

### 参照的是数据顺序，不是上屏通道

`029` 把热键链分成先后三截，三截的消费者不同。

1. 录音过程中，`updatePartial` 与 `confirmSegment` 交出 `isFinal` 为假的转写。`authoritativeText` 为空。消费者是 `handleASREvent` 与悬浮条。这一截不调用 `LLMClient.process`，也不调用 `inject`。
2. 停止之后，`endAudio` 用累积的整段 PCM 做一次定稿。Qwen3 有字则整段替换已确认片段，再 `emitTranscript(isFinal: true)`。会话把 `currentTranscript.displayText` 收成 `effectiveText`。空字符串不进入 `finishTextOutput` 的下半段。
3. `finishTextOutput` 在提示非空时才调用 `client.process`。输入是文本。快速模式的提示是空字符串，这一截不调用。`process` 返回之后，Type4Me 才进入 `inject` / `injectTracked`。

Rime 客户端的宿主字段要的是预编辑或提交。`030` §1.2 把「尚未进入 inject」的文本映成预编辑记录或提交记录，因为接口的宿主是输入法字段，不是菜单栏悬浮条。这一映射是呈现的候选，不是把 `RecognitionTranscript` 或 `InjectionOutcome` 当成端口。

`028` 已把 Type4Me 的交付截排除在识别契约之外。本参照的交付只消费意图。不调用 `TextInjectionEngine.inject`，不调用 `injectTracked`，不进入 `.injecting`。那条通道的做法不写进交付。

### 两条路径只在宿主字段相遇

键盘事件仍走既有键盘路径，产生键盘自己的组合与提交。语音路径不把采样帧、识别记录、改写记录或意图交给那条路径，也不从那条路径读出语音进行到哪一步。`030` §1.4 沿用 `013` 的一句：未取走的键盘事件仍进键盘链。Squirrel 现行 `handle` 在译码之后调用 `rimeAPI.process_key`。语音文本不编码成按键，不插在这次调用前面。librime 里的键盘路径不改。

触发对一枚键盘事件只有两个结果。取走：该事件不进入键盘链，只产生打开或关闭，不写字段。未取走：类型与修饰保持原样，进入键盘链。自有预编辑区间还在时也是如此。此后两段文本在字段上各变成什么，`030` §9 第 6 点记为未知。对不上自己登记区间的意图整笔拒绝。拒绝不改键盘链。

### 部分与定稿不是两级制品

`029` §1：热键链选中的客户端是 `SenseVoiceASRClient`。`SenseVoiceWSClient` 没有构造点。`server.py` 的 `/ws` 会发 `is_final` 为假或真的 JSON，会话不订阅。本链上的部分文本来自 sherpa-onnx 的 `decode`；定稿可以来自 `POST /transcribe`，失败时留下 SenseVoice 片段。

`028` §2 候选 1：两条都能产出文本，修订指针仍由调用方在外面算。`030` §1.1 沿用 `025` 的「一次会话只接一行识别候选」，不把 SenseVoice 与 Qwen3 串成前后两级。本参照同样不串。部分文本与定稿文本是同一条识别记录的两种种类。哪一行制品填这条记录，见文末未知，架构不挑。

### 架构边界

下表只标候选架构上谁碰得到谁。它不是类图。

| 记录或端口 | 读 | 写 | 碰不到 |
| --- | --- | --- | --- |
| 会话 | 打开时的字段标识与范围；此后挂在该标识上的识别记录与改写记录 | 寿命、交付许可、收束标记、自有区间、两条记录 | 键盘组合状态；另一枚会话的范围；`inject` |
| 触发 | 键盘事件子集；采集的静音一类信号；识别侧的定稿信号；失焦信号。均可缺席 | 某一会话的打开或关闭 | 采样帧、文本、宿主字段 |
| 采集 | 设备选择、使用权、会话开闭、设备侧格式变化 | 带格式的有序帧，或无帧并结束 | 热词、识别文本、宿主字段 |
| 上下文 | 来源在该时刻的只读值 | 一份槽位快照 | 模型权重、宿主字段、识别记录 |
| 识别适配器 | 有序帧、热词字符串或它的缺席、会话标识 | 一条识别记录：部分或定稿 | 改写返回值、意图、宿主字段 |
| 改写适配器 | 定稿全文、会话标识、提示或它的缺席 | 一条改写记录 | PCM、宿主字段、部分文本 |
| 呈现 | 识别记录、改写记录、会话是否仍允许交付 | 零条或多条意图 | 采样帧、制品名字 |
| 交付 | 一条意图、交付许可、宿主当前是否接受写入 | 预编辑或提交的相应变更，或拒绝 | 采样帧、键盘组合、`inject` |

## 模块

### 候选包布局

`007` §4 写明：原语禁止的是输入输出类型互相牵连，不禁止同一次进程内顺序调用。下面的目录只为调用方能指出类型放在哪。目录边界不是进程边界。不另设总控包。顺序留在组合处，组合处不是第九个包。

不单设绑定包。`030` 不挑哪一行制品填识别记录；绑定只是端口背后的实例，不改变记录的字段。单设一个只换实例、不换类型的目录，没有独立变化点。

不把键盘路径放进这个布局。未取走事件进入的是现有键盘链。在这里再放一个键盘包，会看起来要改 `process_key`。

- `voice-interface/session/`：会话标识、寿命、许可、识别记录、改写记录
- `voice-interface/trigger/`：打开或关闭
- `voice-interface/capture/`：带格式的有序帧
- `voice-interface/context/`：槽位快照；热词槽投影成一段字符串
- `voice-interface/recognition/`：识别适配器，帧与热词字符串进，部分或定稿出
- `voice-interface/rewrite/`：改写适配器，定稿全文进，改写记录出
- `voice-interface/presentation/`：预编辑意图与提交意图
- `voice-interface/delivery/`：一条意图的应用或拒绝

类型的归属用来让依赖单向、无环。这是候选放置，不是另一套状态。

- 会话标识、识别记录、改写记录、寿命与许可放在 `session/`。`recognition/` 与 `rewrite/` 只依赖这些类型并返回记录。`session/` 不依赖适配器实现。
- 帧的类型放在 `capture/`。`recognition/` 依赖帧类型。`capture/` 不依赖 `recognition/`。
- 快照类型放在 `context/`。投影出的热词字符串是一段文本。`recognition/` 依赖的是这段文本，不引用 `context/`。组合处读快照，把字符串交给识别适配器。
- 意图类型放在 `presentation/`。`delivery/` 依赖意图与 `session/` 的许可。`presentation/` 不依赖 `delivery/`。
- `trigger/` 只写入会话的开闭。`session/` 不依赖 `trigger/`。

各包公开的类型停在对应边界上：

| 包 | 公开类型停在 | 不放入该包的状态 |
| --- | --- | --- |
| session | 会话记录与迁移 | 采样帧、键盘组合、意图如何写进宿主 |
| trigger | 打开或关闭 | 文本、帧 |
| capture | 帧或结束 | 假设、热词 |
| context | 快照，以及只从热词槽投影出的字符串 | 另外四槽的拼接模板 |
| recognition | 识别记录 | 宿主写入、改写判定 |
| rewrite | 改写记录 | 帧、字段、交付字符串 |
| presentation | 意图 | 通道调用、`inject` |
| delivery | 应用或拒绝 | 识别文本如何产生 |

### 四词测量

测量对象是上一节这八个包。测量不是改结构的指令。四词只测这一次。

清晰：每个目录的边界和箭头可以不读实现就说完。`trigger`、`capture`、`context` 不互相引用。`recognition` 与 `rewrite` 只指向 `session` 里的记录类型，并读入帧或文本。`presentation` 只读记录，`delivery` 只读意图。代价是「字何时进入字段」要同时看 `presentation` 与 `delivery`，一次输入的顺序要在组合处才看全。

内聚：`recognition` 里一起变的理由只有「帧与热词字符串变成部分或定稿文本」。`rewrite` 里一起变的理由只有「定稿全文变成不替换或全文不同」。`delivery` 的公开类型里没有 PCM，也没有改写返回串。代价是会话标识被多处引用；标识与两条记录的定义只放在 `session`，其他包不另造一份寿命或许可。

组合：调用方可以只接识别适配器、改写用恒等；也可以只换改写适配器，帧类型与识别记录字段不动。`delivery` 不拉取 Type4Me 的上屏类型。热词快照没有沉进 `recognition`：该包用不到整份五槽，只接收投影后的字符串，字符串由组合处传入。代价是没有任何一个包被两个互不相关的调用方整份复用成底座；共享的是会话标识与记录，不是一个要整份取走的基类。

优雅：每个拆分对应一个独立变化点。会话寿命相对适配器实现、帧相对文本、热词快照相对识别形参、部分与定稿相对改写、意图的种类相对宿主是否接受写入、开闭信号相对键盘链。部分与定稿不再各占一个包，因为 `030` 把它们收成同一条记录的两种种类。不合并 `presentation` 与 `delivery`：前者回答何时排成哪种意图，后者回答拒绝时字段是否逐字不动，变化理由不同。不增加绑定包与键盘包，理由见本节开头。代价是包的数量等于这些变化点，组合处是唯一同时看见全部端口的地方。

## 接口

本节的记录是候选契约。调用方按这些记录写适配器。记录不是宿主的函数表，也不是 Type4Me 内部结构的字段表。`RecognitionTranscript` 的四个存储字段、`LLMClient.process` 的边界参数，都不进入端口。位置的平台单位、字段标识的平台值，未知处保持未知。

### 会话字段

会话标识与键盘引擎的 `RimeSessionId` 不是同一枚。打开成功时换一枚新标识。作用与 `029` 的 `sessionGeneration` 相同：对不上的结果不写入这一份会话的记录，也不写字段。标识的具体字节形式，本文不给定。

打开成功时写入：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 不透明。识别记录、改写记录、意图都带它 |
| 字段快照 | 打开时记下的宿主字段标识。交付时与当前要写的那一份比较。平台值未知 |
| 范围快照 | 打开时的范围。可以是空选区，表示光标插入点。位置的平台单位未知 |
| 寿命 | 未建立、开放、已关闭 |
| 收束已请求 | 是或否。已请求只说明触发不再把这次当作未收束 |
| 交付许可 | 允许或拒绝 |
| 自有预编辑区间 | 无，或会话自己登记的一段范围 |
| 识别记录 | 空、一条部分文本，或一条定稿文本。新的部分文本整段替换上一条部分文本 |
| 改写记录 | 未到、不替换，或全文不同 |

不设「已应用提交」这一位。`030` §3 不把「提交成功随即关闭」和「同一字段至多一枚允许交付」写回来。应用过的意图可以留在会话里供对照，对照本身不是拒绝理由。

未列出的输入不迁移。

| 当前 | 输入 | 迁到 | 字段 |
| --- | --- | --- | --- |
| 未建立 | 触发打开，且当时能记下字段标识与范围 | 开放，允许交付，收束未请求 | 不动 |
| 未建立 | 打开时字段标识记不下来 | 保持未建立 | 不动 |
| 开放，允许交付 | 部分文本记录，且标识相同 | 仍开放 | 识别记录换成这一条。呈现可另写预编辑意图。不写提交意图 |
| 开放，允许交付 | 定稿文本记录，且标识相同 | 仍开放 | 识别记录换成定稿。改写记录仍是未到。不写提交意图 |
| 开放，允许交付 | 触发给出关闭 | 仍开放，允许交付，收束已请求 | 不动。关闭不调用改写，也不写字段 |
| 开放，收束已请求，识别记录已是定稿 | 改写记录到达，且标识相同 | 仍开放 | 改写记录写入。候选顺序在这一行写出提交意图 |
| 开放，允许交付 | 预编辑意图被宿主应用 | 仍开放；自有区间换成该范围 | 只有该区间的预编辑被替换 |
| 开放，允许交付 | 提交意图被宿主应用 | 仍开放；自有区间变为无 | 该范围成为提交文本。不因这一笔进入已关闭 |
| 开放 | 字段标识偏离快照 | 仍开放，拒绝交付 | 不动。识别与改写可以继续留在记录里 |
| 开放，收束已请求 | 呈现不再持有未发出的意图，且自有区间为无 | 已关闭 | 不动 |
| 已关闭 | 迟到的识别、改写或意图 | 保持已关闭 | 不动 |

标识不同的记录不进入上表。同一字段上可以有另一枚仍允许交付的会话。范围在宿主上对不上时，该条意图整笔拒绝。这是逐条拒绝，不是打开时只留一枚。

失焦不是会话标识。触发不把它当成关闭，并且字段标识也未偏离快照时，上表不迁移。一段失焦是否等于字段标识偏离，未知，不在迁移表里并成一行。

空定稿是正常的识别记录。它不写意图。电平从未越过说话阈值、因而没有定稿可送去改写时，同样不写意图。`029` §6：这两种情况不进入会调用 `inject` 的那一段。本端口停在「不写意图」。

核对：按候选顺序，部分文本到达时，提交意图是否尚未写出？定稿已写入识别记录、改写记录仍是未到时，提交意图是否仍未写出？会话标识不一致，或寿命已关闭，或交付许可为拒绝时，预编辑文本与提交文本是否都保持不动？

### 预编辑与提交意图

呈现输出的一条意图只含四字段。

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与会话记录相同才可以应用 |
| 范围 | 见下 |
| 字符串 | 部分文本，或定稿原文。没有纠错分数时不取改写返回串 |
| 种类 | 预编辑，或提交 |

意图上没有采样帧，没有制品名字，没有键盘事件，没有 `InjectionOutcome`。

范围沿用 `030` §6，交付不重新解释：

- 种类为预编辑，且尚无自有区间：范围等于打开时的范围快照。应用之后，把写下的那段记为自有区间。
- 种类为预编辑，且已有自有区间：范围等于该区间。提交文本不增加。
- 种类为提交，且已有自有区间：范围等于该区间。应用后区间登记变为无。字段上不留下预编辑副本再加一段提交。
- 种类为提交，且无自有区间：范围等于打开时的范围快照。

一笔事务处理一条意图。检查按下面的顺序。任一项失败：不调用宿主写入，自有区间登记也不前进，字段与检查前逐字相同。

1. 意图的会话标识等于这一份会话的标识。
2. 寿命是开放。
3. 交付许可是允许。
4. 当前字段标识等于打开时的快照。
5. 宿主当前接受写入。
6. 种类为预编辑时：字符串等于会话里当前识别记录的文本。识别记录仍是部分，或已是定稿但改写未到，都可以。改写返回串不能出现在预编辑意图里。
7. 种类为提交时：字符串等于识别记录里的定稿全文。不取改写返回串。改写记录仍是未到时，事务不因「改写未到」拒绝这段定稿全文，也不另造一段文本。

呈现的候选顺序，对齐 `029` 的三截，并在 `inject` 的位置停住：

1. 每条部分文本至多一条预编辑意图，字符串是该部分文本。零条提交意图。
2. 定稿写入识别记录、改写仍未到：不写提交意图。候选是再写一条预编辑意图，字符串换成定稿全文，替换自有区间。
3. 改写记成不替换，或全文不同但没有纠错分数：一条提交意图，字符串是定稿原文。
4. 写出上述意图后，交付按上一列检查应用或拒绝。不调用 `inject`，不调用 `injectTracked`。

`030` §8 的反论仍然有效：有的宿主在说话结束时期望文档里已经有字；目标宿主在定稿之后还留不留得住预编辑，未测量。因此上面的顺序保持候选。即便呈现改成收束时先提交原文，意图的种类仍然只是预编辑或提交，第 7 项仍只接受定稿全文，不把「改写已经到达」收成拒绝条件，仍然不调用 `inject`。事务不另加「同一会话至多成功一笔提交」。`030` 没有把这句写回来，也没有测量第二次提交在文档历史上留下几段。

应用这条意图的是宿主字段上的预编辑写入或提交写入。`030` §6 点过 Squirrel 的 `show(preedit:selRange:caretPos:)` 与 `commit(string:)`，并写明复用会碰到控制器上那份键盘预编辑缓存。那是距离。本参照不把这次复用写成已经接好的通道。

核对：交付被完全断开时，呈现是否仍能列出意图，且定稿原文仍可读取？连续三条部分文本是否可以只有预编辑意图、没有提交意图？

### 识别适配器的输入输出

对外只交一条记录。`029` 引用的 `RecognitionTranscript` 把已确认片段、部分文本、权威文本和 `isFinal` 放在同一结构里。`isFinal` 为假时权威文本为空，展示文本退回片段与部分文本的拼接；定稿时权威文本等于当时的拼接。适配器把「当时要展示的整段」收成一个文本字段，种类标明部分或定稿。`confirmedSegments` 不出现在记录里。返回值里没有「修订的是哪一条」。`028` 与 `030` 都不补这个字段。

输入：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 打开成功时发出的那一枚 |
| 有序帧 | 见下表。采集按顺序交出。识别适配器不打开麦克风 |
| 热词字符串 | 缺席，或一段文本。缺席不是空字符串。它不是五槽对象 |

每一帧：

| 字段 | 候选取值 |
| --- | --- |
| 编码 | PCM16，小端 |
| 采样率 | 16000 |
| 声道 | 1 |
| 字节 | 这一段的样本字节，顺序与采集交出的顺序相同 |

格式写在帧上。`029` 记下 `AudioCaptureEngine` 的 `sampleRate`、`targetFormat` 与 `server.py` 的 `SAMPLE_RATE`、`BYTES_PER_SAMPLE` 都是这组数。这是本适配器候选要接受的格式，不是「当前加载了哪个模型」的隐含值。`029` 还记下默认一块 6400 字节、约 200 毫秒，以及停录时冲掉不足一块的尾巴。块长不是记录字段。更换块长不更换本表。

输出：

| 字段 | 部分文本 | 定稿文本 |
| --- | --- | --- |
| 种类 | 部分 | 定稿 |
| 文本 | 当时要展示的整段。可以替换上一条部分文本 | 定稿全文。可以是空字符串 |
| 会话标识 | 与输入相同 | 与输入相同 |

新的部分文本替换会话里的上一条部分文本。替换留在会话内，不因此写出提交意图。空定稿不写意图。使用权不成立时，采集输出为结束且不产生帧，识别适配器不被要求把这件事报成一段识别成功。

哪一个入口填这条记录，`030` §9 第 1 点不挑：`POST /transcribe`、`024` 已测的 `feed_audio`，或其他整段入口，都还对得上「文本出」。`/ws` 不在 `029` 的热键链上，不当作这条记录的部分文本来源。不用 SenseVoice 时，定稿之前有没有另一段部分文本，未知。没有部分文本时，呈现可以只有定稿之后的预编辑意图。不补一段假的部分文本。

核对：只喂帧、不提供宿主字段时，适配器是否仍交出记录且不写预编辑？连续两条部分文本是否都没有提交意图，且会话里只留着后一条的整段文本？

### 改写适配器的输入输出

输入是定稿全文与会话标识，外加提示的缺席或在场。不是部分文本，不是 PCM。`029` §7：`LLMClient.process` 的输入是字符串；sherpa 这条链要到 `finishTextOutput` 才调用；快速模式提示为空则不调用。`029` 里约 15 秒的等待、短文本字数豁免、片段替换与守卫，是 Type4Me 会话自己的条件，不进入本记录的字段。

输入：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与定稿那条相同才接受 |
| 定稿全文 | 识别记录种类为定稿时的文本 |
| 提示 | 缺席，或一段文本。缺席不是空字符串。空字符串与缺席同样视为不调用 |

输出：

| 字段 | 候选含义 |
| --- | --- |
| 会话标识 | 与输入相同 |
| 原文 | 送进去的定稿全文，原样保留 |
| 返回串 | 模型返回的字符串。未调用、失败或空结果时缺席 |
| 判定 | 不替换，或全文不同 |

判定只做全文逐字比较：

- 提示缺席，或调用失败，或返回串缺席，或返回串与原文逐字相同：记成不替换。
- 返回串与原文逐字不同：记成全文不同。

没有这样一对数字：某一仓库路径、某一次 MLX 量化、替换文本的错误少于识别假设。记成全文不同时，返回串留在改写记录里供核对，不写入预编辑意图或提交意图。呈现使用原文。「不替换」和「全文不同但不上屏」对意图字符串的效果相同，都是原文。改写记录里二者仍然分开，用来核对比较做过没有。

提示在场时，适配器才把定稿全文与这段提示交给一个返回字符串的实现。返回值只有字符串，没有「不替换」这一种类；种类由上面的比较填上。`028` §2 候选 2：Type4Me 的 `LLMClient` 可以当远程绑定的一种调用形状。它不证明替换更正确。本机实现是不是 mlx-lm，不由这条记录决定。

恒等实现始终交出不替换，并在原文栏留下定稿全文。换成另一个实现时，识别适配器的帧输入与识别记录字段不改。

核对：对同一条定稿把实现换成恒等之后，采集与识别适配器是否无需改动？输出里是否仍能读出原文？全文不同、且纠错分数这一格为空时，提交意图的字符串是否仍是原文？

### 热词槽

上下文的输出是一份槽位快照：名字到值的映射，不是某一个模型的提示词。同一次汇集可以交给组合处。来源读不到时，对应槽位缺席。缺席用「没有这个槽」表示，不用空字符串顶替，也不用空列表顶替。

`030` §9 第 4 点点名的五个槽是 `host_app`、`field_role`、`cursor_before`、`hotwords`、`corrections`。快照的候选形状：

| 槽位 | 值 | 缺席 |
| --- | --- | --- |
| `host_app` | 一段文本：宿主应用标识 | 给不出标识 |
| `field_role` | 一段文本：输入框角色 | 读不到角色 |
| `cursor_before` | 一段文本：汇集瞬间、光标之前、已经在字段里的文本。不含本会话的预编辑 | 宿主不提供周围文本 |
| `hotwords` | 有序的词文本。顺序是这次汇集看到的顺序 | 来源没有词 |
| `corrections` | 有序对。每对是 `src_text` 与 `dst_text` 两段文本 | 来源没有对 |

汇集是只读的。一次汇集不修改宿主字段，不修改键盘组合，不修改模型权重。候选时刻是会话打开时读一次。不在预编辑写入之后把预编辑读回 `cursor_before`。四槽全缺席时快照仍成立。识别假设、会话标识、采样帧都不写入槽位。

识别适配器的热词输入只来自 `hotwords` 这一个槽。投影规则跟 Type4Me 已经写在服务进程里的装入方式对齐，并且只作用于这个槽：

```python
# 源：dev-docs/refs/code/type4me/Sources/qwen3-asr-server/server.py:388-391，提交 2835334
if args.hotwords_file and Path(args.hotwords_file).exists():
    words = [w.strip() for w in Path(args.hotwords_file).read_text().splitlines() if w.strip()]
    if words:
        _hotword_context = " ".join(words)
```

候选投影：

- `hotwords` 缺席：热词字符串缺席。不写成 `""`。
- `hotwords` 在场：去掉每条两端空白，丢掉空白项，用单个空格拼成一段字符串。这一段就是识别适配器的热词字符串。
- `host_app`、`field_role`、`cursor_before`、`corrections` 不进入这段字符串。不给它们补分隔符，也不把缺席写成空字符串再拼进去。
- 改写适配器的提示不是这五个槽拼出来的。提示缺席与否单独放在改写输入上。四个槽进入提示的拼法，未知，不补模板。

`029` §6：定稿 HTTP 体是原始 PCM，热词不在这个体里。进程级 `context` 与客户端拿来做清洗的 `calibrationHotwords` 不是同一个参数位置。本端口不把清洗器的内部表收成第六个槽。识别记录向外仍然只有种类、文本、会话标识。

核对：清空全部来源之后，识别适配器是否仍接受「热词字符串缺席」的输入并产出记录？同一份非空 `hotwords` 是否只投影一次，而不是为改写适配器再写一份来源？

## 关键实现决定

每条都是候选决定。追溯指 `028`、`029` 或 `030`。异议清单为空，所以没有条目被吸收。未知栏只指向已经记下、本文不补的点。

### 决定 1：接口是会话上的组合，Type4Me 进程不是端口

候选决定：调用方看见的是八个包上的记录，不是一次从采样到上屏的函数，也不是 Type4Me 可执行文件或 `type4me://toggle`。同一次进程内可以按架构一节的顺序调用这些端口。组合处不命名成一种模式，不另设总控包。

追溯：`028` §1 拒绝把三截焊成一个语音输入函数；`028` §2 舍弃可执行文件与 URL 端口。`030` §1.5 沿用这两条舍弃。`030` §2 写明模块是同一次组合里的分工。

异议：清单为空，没有要求恢复总函数或把 Type4Me 进程当成输入法的条目。未知：无新的一项。制品填哪一行，仍是决定 4 的未知。

### 决定 2：先部分与定稿，再对定稿全文改写

候选决定：识别适配器在会话仍开放时可以多次交出部分文本；停止并得到定稿之后，改写适配器才接收定稿全文。改写不吃采样帧，不吃部分文本。提示缺席则不调用模型，改写记录直接为不替换。

追溯：`029` §5 部分文本的消费者不是 `process`；`029` §6 定稿先成为 `effectiveText`；`029` §7 `process` 位于定稿已经取出之后，且快速模式不调用。`030` §1.1 按这个顺序收成适配器。`028` §2 写明改写截的输入已经是文本。

异议：清单为空。未知：`030` §9 第 2 点，不用 SenseVoice 时定稿之前有没有另一段部分文本。没有就不补假的部分文本。呈现可以只有定稿之后的预编辑意图。

### 决定 3：部分与定稿共用一条识别记录，不串成两级

候选决定：识别记录只有种类、文本、会话标识。种类取部分或定稿。新的部分文本整段替换上一条。不暴露 `confirmedSegments`，不增加修订指针字段，不把 sherpa-onnx 与 Qwen3 做成前后两个识别包。

追溯：`028` §2 候选 1，返回值没有修订指针，也不把两级写成前提。`029` §1 与 §5：热键链的部分文本不是 `/ws`，`SenseVoiceWSClient` 没有构造点；`029` §5 的 `emitTranscript` 在同一次转写里区分 `isFinal`。`030` §1.1、§1.5、§4 把两种种类收进一条记录。

异议：清单为空。未知：`030` §9 第 1 点，这一行接 `POST /transcribe`、`feed_audio` 还是别的整段入口。本文不挑。`/ws` 不进入这条记录的部分种类。

### 决定 4：交付是预编辑或提交意图，停在 inject 之前

候选决定：意图四字段是会话标识、范围、字符串、种类。种类只有预编辑与提交。部分文本至多产生预编辑意图。改写记录到达后产生一条提交意图，字符串是定稿原文。应用或拒绝之后组合返回。不调用 `TextInjectionEngine.inject`，不调用 `injectTracked`。Type4Me 那条上屏通道的做法不写入 `delivery/`。

追溯：`028` §2 候选 3 与 §3，交付不调用 `inject`，少写的不是把上屏改成另一条通道。`029` §8 与 §9，`inject` 的调用点在改写之后，部分文本的消费者不是它。`030` §1.2、§6、§8 把将要交给 `inject` 的字符串改记成提交记录，并在该位置停住。

异议：清单为空。未知：`030` §8 与 §9 第 5 点。定稿之后预编辑是否还留在字段上，未测量，所以「先预编辑、再一条提交」保持候选。`show` / `commit` 会不会改写键盘预编辑缓存，仍是距离，不收成已经接好的通道。第二次提交在文档历史上留下几段，未测量，事务不为此增加「至多一笔」。

### 决定 5：全文相同则不替换；没有纠错分数则差异不上屏

候选决定：改写适配器用定稿全文与返回串做逐字比较。相同、未调用、失败或空结果，记成不替换，原文留下。全文不同仍写入改写记录。纠错分数这一格是空的，呈现不把返回串放进意图。提交字符串保持定稿原文。

追溯：`028` §2 候选 2，Type4Me 的返回值只有字符串，「不替换」由适配器与原文比较得到，且不证明替换更正确。`030` §1.3 与 §5 把比较材料收在全文上，并写明没有 MLX 纠错分数时差异不上屏。`029` §7 只提供调用点与「失败时退回识别定稿」，没有分数。

异议：清单为空。未知：`030` §9 第 3 点。点名仓库路径、并且在 MLX 上低于识别假设的那对数字，仍无。本文不补阈值，也不从别的 CER 表里挑一档。

### 决定 6：收束已请求与关闭分开，字段偏离只拒绝交付

候选决定：触发给出关闭时，会话仍开放且允许交付，字段不动。发出关闭的一方不因此获得写字段的权利。提交意图应用成功不把寿命迁到已关闭，也不关掉交付许可。能进入已关闭的条件只有：收束已请求，呈现不再持有未发出的意图，且自有区间为无。字段标识偏离快照时，交付许可改为拒绝，识别记录与改写记录可以继续留着，不改写新字段，也不再改写旧字段。同一字段可以有另一枚仍允许交付的会话；范围对不上则该条意图拒绝。

追溯：`029` §6，`handleASREvent` 先核对 `sessionGeneration`，对不上不写入 `currentTranscript`；停止先改 `.finishing` 再取定稿，定稿本身还不是上屏。`030` §3 用会话标识担任同一件事，并给出上表这组迁移，明确不把「提交成功随即关闭」和「同一字段至多一枚允许交付」写回来。`028` 没有另一套会话字段。

异议：清单为空。未知：字段标识的平台值；一段失焦或权限提示是否等于字段偏离；同一宿主字段能否同时持有两段互不覆盖的预编辑。这三件都不收成新的迁移。`030` §3 已把失焦与字段偏离分成两路，本文保持两路。

### 决定 7：未取走的键进入键盘链，不改 librime

候选决定：取走的事件只产生打开或关闭，不写字段，不进入键盘链。未取走的事件，不论自有预编辑区间是否还在，都原样进入既有键盘链。链上仍是译码与 `process_key`，不因语音会话增加分支。语音路径不向键盘链提交帧、记录或意图，也不读取键盘组合来判断语音进行到哪一步。librime 的键盘路径不改。

追溯：`030` §1.4 与 §7，并点名 Squirrel 的 `process_key` 调用位置。`030` §1.5 舍弃改键盘路径，也舍弃把未取走事件拦在链外。`028` 与 `029` 不把识别文本写成按键。

异议：清单为空。未知：`030` §9 第 6 点。自有预编辑仍在、未取走键已经进入键盘链之后，两段文本如何同时留在字段上。对不上的意图整笔拒绝。不把「先停在链外」写回来填这个未知。

### 决定 8：热词只有一槽进入识别字符串，另外四槽不拼接

候选决定：快照保留五个槽，缺席不是空字符串。识别适配器只接收 `hotwords` 投影出的一段空格分隔字符串，或该字符串缺席。另外四槽留在快照上，不进入识别字符串，也不进入改写提示。改写提示是单独的一段文本或然缺席。帧的字节里不放热词。

追溯：`028` §2，热词不是五槽；`028` §3，少写的包括热词字符串的位置，不包括另外四槽。`029` §6，热词不在 `POST /transcribe` 的 HTTP 体里。`030` §2、§4 与 §9 第 4 点，不新写拼接，不把缺席改成空字符串。投影用的空格连接来自 `server.py:388-391`，与 `030` 已核对的进程级 `context` 一致。

异议：清单为空。未知：`030` §9 第 4 点。`host_app`、`field_role`、`cursor_before`、`corrections` 进入热词字符串或改写提示的拼法，仍然未知。本文不补模板。个人词、纠错对与键盘路径上的用户词是不是同一存储，`007` 记过未知，这里同样不规定存储。

### 决定 9：帧格式写在帧上，块长不进入端口

候选决定：本适配器接受的帧是 PCM16 小端、16000、单声道。这三个数写在帧上。采集在使用权不成立时无帧并结束。`029` 观察到的 6400 字节默认块、约 200 毫秒，以及开始处跳过样本，不成为识别记录或帧记录的字段。更换块长不更换识别适配器的输入类型。

追溯：`028` §2 候选 1，识别沿用 PCM16、16 kHz 这一截契约。`029` §4 给出 `AudioCaptureEngine` 的格式与默认块长，并分开写了 VAD 的 `skipInitialSamples`。`030` §2 只把编码、采样率、声道收进帧的候选形状。

异议：清单为空。未知：别的制品若要求另一组格式数，帧上的字段仍然能表达；那一组数是不是本适配器的数，要等决定 3 留下的入口选择。本文不把 16000 写成全部制品的隐含值，也不另补一个块长。

### 决定 10：空角色与空分数不改记录的字段

候选决定：识别入口尚未挑定时，识别记录的三个字段仍然是种类、文本、会话标识。纠错分数空着时，改写记录仍有原文、返回串与判定，意图字符串仍取原文。快照四个槽对不上形参时，槽可以缺席，热词字符串可以缺席，两个适配器的输入类型不因此改成另一家报文。恒等改写与「只回放给定文本、不读权重」的识别替身，用来按本节的核对句对照记录。替身不另造端口字段。

追溯：`028` §2，契约相同的那一截才接，对不上的不因为仓库里已有上屏就换掉。`030` §1.3、§5、§9 第 1 与第 3 点，入口不挑、分数为空，记录形状先照此成立。`029` 提供的是调用点，不是一份已经选定的 Rime 侧制品。

异议：清单为空。未知：决定 3、决定 5、决定 8 已经列出的三项。空着的格子不改成另一套产品的请求字段，也不改交付的四字段。

## 仍然未知，且本参照不补

下列各项 `030` §9 与 §8 已经记下。这里只列与端口有关的那几条，避免把未知写成另一种倾向。

1. 识别记录接 `POST /transcribe`、`feed_audio`，还是别的整段入口。`/ws` 不在热键链上。决定 3 不挑。
