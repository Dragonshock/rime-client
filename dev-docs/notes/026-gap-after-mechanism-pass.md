下文原语均指 `dev-docs/notes/007-derivation-voice-input-primitives.md`。豆包输入法只作机制对照。公开源码与已有笔记够用，本文没有调用 REA。

- `021` 读函数体、`024` 保存了第 0 次计时会话的字符串：`moona3k` 的下一次 `state.text` 可以不再以上一次全文为前缀。同一次会话的块序 4，把已交出字符串里的逗号换成了句号。`mlx-audio` 的 Qwen3-ASR 与 Voxtral 的 `step`，下一次返回值不改写上一次已经交出的那个对象。

## 1. 已读的 MLX 返回值仍然没有「修订的是哪一条」

**未知：** 哪一份已读返回值自己标明：这一次改的是哪一条先前假设。三份 Python 入口都没有这个字段。和它绑在一起、这次仍没有对照的还有两句：`moona3k` 强制前缀所覆盖的字符，在真实音频上会不会变；Voxtral 类注释里的 hypothesis flip，会不会让已经打印出去的追加切片在语义上作废。

`021` 通读的 `feed_audio` 在新整段不以旧整段为前缀时只把次数加一。次数不是假设标识，也不是被改字符串的下标：

```python
# 来源: https://raw.githubusercontent.com/moona3k/mlx-qwen3-asr/main/mlx_qwen3_asr/streaming.py 的 feed_audio
        if state.text != prev_text:
            state._text_updates += 1
        if prev_text and state.text and not state.text.startswith(prev_text):
            state._rewrite_events += 1
```

`024` 的 10 次都是 `rewrite_events=7`，返回值仍是整份 `StreamingState`。`stable_text` 在第 0 次计时会话里从块序 2 起一次比一次长；其余 9 次的字符串没有保存。已经放进 `stable_text` 的字会不会被改掉：未证明。块序 4 那次标点变化没有对齐到「强制前缀的 token」还是「被回退的尾部」，所以强制前缀覆盖的字符会不会变，仍然未知。

`mlx-audio` 的 `StreamingResult` 与 Voxtral 的 `list[str]` 都不接收上一次已经返回的对象。翻转若发生，返回值里没有一项记载它。

**存在依据：** 原语 4：每条假设是一段文本，并标明它修订的是哪一条先前假设；更晚的假设可以替换更早假设的文本，替换停在会话里。用户原话要求填补这一处空白，豆包只作对照。`021` 第 7 节写明：要说某一份返回值自己满足这句，缺的是字段或等价对照，不是再把调用方记住的上一条标识叫成模型字段。`025` 第 5 节把「三份已读 MLX 返回值里的修订指针」留空。`002` §4.1 的 `commonPrefix` 比较的是调用方已经拿到的两段字符串；该节三步在原文里仍标成候选（待用户确认）。本文没有新的反汇编。

**现在是否需要补证：** 不需要把 vLLM 上拒绝非 vLLM 的整段覆盖再读一遍。`018` 与 `025` 都没有把它写进 MLX 绑定。不需要调用 REA。若要说某一份返回值自己满足原语 4 的修订标记，需要字段，或一份对照能指出改的是哪一条、从哪一段字符开始。在此之前，调用方自持上一条标识，仍然只是 `021` 已写下的候选包装。Voxtral 的翻转有没有让已打印切片作废：要说它发生，需要另有观测；没有观测时，不从 `list[str]` 读出作废。强制前缀与 `stable_text` 已放入的字：不把第 0 次「只变长」写成 10 次都不变，也不写成已经测得会被改掉。

## 2. 四槽进入一段字符串的拼法，仍然没有槽位表

**未知：** `corrections`、`cursor_before`、`host_app`、`field_role` 的文本，以及 `hotwords` 的有序词，哪一个名字、用空格还是逗号，进入已有入口的那一段 `context`、`system_prompt` 或 `prompt`。`022` 读过的论文、模型卡和源码没有这张表。

同名形参已经对上的，不是这条未知。`hotwords: Optional[List[str]]` 只在 `mlx-audio` Python 的 `generate`，非空时用 `", "` 拼进 `system_prompt`。`stream_transcribe` 自身没有这个形参。官方 `qwen_asr`、`moona3k`、`mlx-audio` Swift 的文本形参是一段 `context` 字符串；Hugging Face 模型卡的形参名是 `prompt`。这几处类型都不是五槽那份名字到文本的映射。Voxtral Python 的 `create_streaming_session` 与 Swift 的 `init` 没有这些名字。

**存在依据：** 原语 6：槽位是名字到文本的映射，不是某一个模型的提示词格式；同一份快照可以同时交给识别流与改写流；来源读不到时槽位缺席，快照仍然成立。`011` 把一次汇集写成 `host_app`、`field_role`、`cursor_before`、`hotwords`、`corrections`。用户原话要求接口不依赖某一家实现的内部结构，豆包只作对照。`022` 第 4 节把拼接方式留成未知，不补模板。`025` 第 3.2 节与第 5 节沿用这句。`003` §2.4 的 `HOTWORDS`、`USER_MODIFY`、`CUR_CONTEXT`、`BOT_DESC` 是样本内部的分函数；`022` 写明这张投影不抄到 Qwen 或 Voxtral 的形参上。

**现在是否需要补证：** 不需要新写一套分隔符来充当槽位表。空快照时，已读材料允许系统提示为空，Voxtral 的构造参数里本来就没有文本槽，两条都能继续出文本。原语 4 的空快照条款不依赖槽位名。四槽没有形参，这一件已经读过，不需要在同一份 `init` 里再找同名参数。未知时，不把缺席槽写进 `context` 或 `system_prompt` 来冒充落点，也不把缺席改成空字符串再拼进去。
