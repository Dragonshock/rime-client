# 008-derivation-voice-session-commit-and-keyboard-coexistence：语音会话、上屏事务与键盘共存

本文只推导三件事：一次语音优化输入的会话（session）状态机；预编辑文本（preedit）与提交文本（commit）如何收成一笔可拒绝的事务；语音态与键盘输入如何共用宿主字段，同时不改键盘路径。倾向一律是候选。

推导使用的原语来自 `dev-docs/notes/007-derivation-voice-input-primitives.md`。采集（capture）、识别流（recognition stream）、改写流（rewrite stream）、上下文（context）与绑定（binding）的内部做法不在本文重写；本文只消费它们已经规定的输入输出。与 Squirrel 现行树的对照放在最后一节，那一节是距离，不是设计。

## 1. 推理链

### 1.1 为何是这三件事，而不是一个「语音态」

007 把语音优化输入拆成九条可以独立替换的原语。其中和「字什么时候算进宿主字段」直接相关的是四条：会话决定迟到结果还能不能写；触发（trigger）只产生开闭信号，不产生文本；呈现（presentation）把假设与改写结果排成变更意图；交付（delivery）把意图应用到宿主字段，或整笔拒绝。

这四条如果收成一个叫「语音态」的对象，开闭、假设修订、预编辑、提交会变成同一次状态迁移。007 已经舍弃了这种焊法：

- 焊法 C：识别假设即提交。部分结果会被更晚的假设改字。每来一条就写一次提交，修订会变成宿主文档历史上一串追加。
- 焊法 E：语音文本伪装成键盘事件灌进键盘组合。用户要求键盘路径保持原样可用。改写要撤销的应是一段文本，不是组合引擎的状态。
- 焊法 F：手势、模型实例、宿主字段合成一个对象。失焦可以发生在手势尚未结束时；模型结果可以发生在手势结束之后。
- 焊法 G：把「预编辑还是提交」写死在某一次宿主调用里。种类是意图的属性，通道是宿主接受哪种写入。二者不是同一个选择。

因此本文的方向是三份分开的记录，而不是一个总状态：

1. 会话记录回答「这是不是同一次、现在还许不许写」。
2. 事务回答「这一条意图是整笔写上，还是整笔不动字段」。
3. 共存约束回答「未被取走的键盘事件何时可以原样进入既有键盘链」。

三者使用同一枚会话标识互相引用，但不共享键盘组合的状态。

### 1.2 舍弃的状态机

**舍弃甲：录音中 / 润色中 / 上屏完成三段式。** 这种分段把触发的开闭、改写流是否返回、交付是否写完焊进同一个枚举。替换「按住为开放」为「切换一次为开放」时，枚举的含义跟着变，触发原语的核对句就不再成立。识别假设的修订也不会在枚举里留下位置：部分结果既不是新的一段，也不是提交。

**舍弃乙：触发的关闭信号立刻等于会话关闭。** 007 第 4 节的候选配对是：部分假设只产生预编辑意图；改写流返回之后才产生一次提交意图；交付只在会话允许时执行。改写结果常常晚于松开、静音或定稿这些关闭信号。若关闭信号立刻把交付许可关掉，这条配对无可交付的时刻。触发原语又规定关闭信号本身不是提交文本，发出关闭的那一方并不因此获得写字段的权利。所以「收束已请求」与「会话已关闭」不能是同一位。

**舍弃丙：失焦即销毁会话，并清掉尚未提交的假设。** 原语 1 写明失焦信号不是会话标识，它只作为触发可消费的一个信号出现，不直接销毁识别流里的中间假设。字段标识相对打开时的快照发生变化，拒绝的是此后的交付，不是假设本身。把失焦做成析构，会回到焊法 F。

**舍弃丁：用键盘引擎的会话标识充当语音会话标识。** 键盘会话的寿命按键盘组合来算：焦点离开时组合可以还在，控制器销毁时会话才销毁。语音会话的关闭不修改已经写进文档的提交文本，也不读取键盘组合。两套标识若共用，语音关闭会拆掉键盘组合，或键盘失焦会丢掉语音假设。本文把键盘会话留在键盘路径里，语音会话另记一枚标识。

**舍弃戊：每条部分假设一笔提交，再用稍后的提交覆盖。** 覆盖若是第二次 `提交`，文档历史里已经有过第一段字。原语 7 规定同一次会话里更晚的假设只产生对预编辑的新意图，不因为又来了一条假设而追加提交。预编辑的替换发生在会话自有的可替换区间上，不进入提交文本。

**舍弃己：把语音字符串编码成按键，交给既有 `process_key`。** 这是焊法 E。键盘路径的输入类型是键盘事件；语音交付的输入类型是已经决定的文本变更。共存若靠灌键实现，键盘路径的组合状态就被语音改写了。

**舍弃庚：在键盘路径内部增加语音分支。** 例如在按键处理函数里判断「现在是不是语音」再决定是否调用组合引擎。判断本身就是对键盘路径的修改：未被取走的事件不再原样进入原有分支。本文把分流放在键盘链之外；进入键盘链之后的函数行为不因语音而出现第二套分支。

**舍弃辛：关闭之后补一次「清预编辑」的写入。** 原语 1 规定会话关闭之后到达的结果不交付。清预编辑也是一次对宿主字段的写入。若关闭已经发生，这笔清理会被拒绝，预编辑区间就留在字段上；若让关闭自己去清，发出关闭信号的触发就获得了写字段的权利，与原语 2 冲突。能写字段的最后时刻，是会话仍允许交付的时候。

### 1.3 留下的分法

留下的候选是下面的分工。

会话只有两段寿命用语，外加两位正交标记：

- 寿命：未建立、开放、已关闭。已关闭之后，这枚标识不再接受任何交付。关闭不回滚已经写进文档的提交文本。
- 标记一：触发收束是否已请求。已请求只说明触发不再把这次当作未收束；交付许可不因这一位单独关掉。
- 标记二：允许交付或拒绝交付。拒绝的原因来自原语 1 与原语 8：会话标识不一致、寿命已关闭、字段标识偏离打开时的快照、宿主当前不接受写入。假设可以继续留在会话里。

呈现不写字段。它输出零条或多条意图。每条意图只带会话标识、范围、字符串、种类（预编辑或提交）。事务是交付对**一条**意图的判定：检查通过则整笔应用，任一检查失败则宿主字段与应用前逐字相同。

键盘共存不进入上述寿命枚举。它是一条约束：键盘链被调用的那一刻，字段上不存在仍由语音事务登记、且尚未由语音事务结束的预编辑区间。结束该区间的意图由呈现给出，由交付在会话仍允许时应用。键盘链拿到的事件保持原来的类型与修饰，不携带假设文本。

007 第 4 节「部分假设只走预编辑、改写返回后至多一次提交」仍只是呈现的候选配对，不是事务的不变量。事务对两种意图序列都成立：连续的预编辑意图互相替换自有区间；提交意图至多成功应用一次。哪一种序列被呈现发出，见第 4 节，不写进事务的检查项。

## 2. 与 007 原语的对应关系

| 本文的记录或约束 | 对应原语 | 本文使用的不变量 | 本文没有改写的部分 |
| --- | --- | --- | --- |
| 会话标识、寿命、交付许可 | 原语 1 会话 | 标识不同的结果不写进彼此的范围；关闭后不交付；关闭不修改已提交文本；字段标识偏离快照则拒绝交付，假设仍留在会话内；失焦不是会话标识 | 不规定失焦多久算字段变化 |
| 「收束已请求」与「已关闭」分开 | 原语 1 与原语 2 | 关闭信号不是提交文本；发出关闭信号的一方不因此获得写字段的权利；交付只在允许时执行 | 不规定触发用按住、切换、静音还是定稿 |
| 意图与事务 | 原语 7 呈现、原语 8 交付 | 意图只有标识、范围、字符串、种类；更晚的假设不因此追加提交；呈现不发明改写文本；拒绝时不做「临时先上屏」；语音文本不经键盘组合再进字段 | 不规定通道是哪一次宿主调用，不规定另一条通道的做法 |
| 键盘事件取走或原样进入 | 原语 2 触发、原语 8 交付 | 被取走的事件不进入键盘组合；未被取走的事件原样进入；触发不读取键盘组合状态；键盘组合不读取识别假设 | 不改键盘链内部的组合、候选与上屏顺序 |
| 假设修订链留在会话内 | 原语 4 识别流、原语 5 改写流 | 假设的替换发生在会话内，不自动变成宿主写入；改写输出要么不替换，要么替换为另一段文本，二者都保留原假设；改写流不持有宿主字段 | 不规定哪一件制品担任哪一个角色 |

原语 3、原语 6、原语 9 在本文只作为边界出现：采集的帧不进入事务；上下文快照不是会话状态；绑定更换不改变意图的形状。它们的缺口仍以 007 第 5 节为准，本文不补制品契约。

核对沿用 007 的问法，并加上本文多出来的两位：

- 任取一条结果，会话标识不一致，或寿命已关闭，或交付许可为拒绝：预编辑文本与提交文本是否都保持不动？
- 触发已经发出关闭、但呈现尚未发出提交意图时：字段是否尚未因此多出一段提交文本？
- 连续三条部分假设、改写结果未到：是否至多对应预编辑事务，而没有三次提交事务？
- 一枚未被取走的键盘事件进入键盘链之后：该链是否仍只消费键盘事件，而不消费采样帧、假设或变更意图？

## 3. 数据契约与状态迁移

本节的记录是候选契约，用来核对状态迁移。它不是宿主接口的函数表，也不是类图。

### 3.1 会话记录

打开成功时写入：

- 会话标识。与键盘引擎的会话标识不是同一枚。
- 宿主字段标识的快照，以及当时的范围快照。范围可以是空选区，表示光标插入点。
- 寿命 = 开放。
- 交付许可 = 允许。
- 收束已请求 = 否。
- 自有预编辑区间 = 无。
- 已应用提交 = 否。
- 假设链为空。此后每条识别假设附在这枚标识上，并标明它修订的是哪一条先前假设；空链不是错误。
- 改写结果 = 未到。到达后是「不替换」或「替换为这段文本」，两种都保留被改写的那条假设原文。

字段标识取什么平台值，本文不确定，见第 5 节。契约只要求：打开时能记下一份，交付时能与「当前要写的那一份」比较是否仍是同一份。比较失败则拒绝，不把快照改写成新字段。

### 3.2 变更意图

呈现输出的一条意图只含：

- 会话标识
- 范围
- 字符串
- 种类：预编辑，或提交

意图上没有采样帧，没有制品身份，没有键盘事件，没有「现在去更新上下文来源」之类的指令。

范围的候选含义：

- 种类为预编辑，且会话尚无自有区间：范围等于打开时的范围快照。应用之后，会话把字段上刚写下的那段记为自有区间。
- 种类为预编辑，且已有自有区间：范围等于该自有区间。应用的可观察结果是自有区间的文本变成这条字符串，提交文本不增加。
- 种类为提交，且已有自有区间：范围等于该自有区间。应用的可观察结果是这段位置上的字成为提交文本，自有区间登记变为无。字段上不留下「下划线草稿再加上一段提交」两份副本。
- 种类为提交，且无自有区间：范围等于打开时的范围快照。

交付不重新解释范围。它若无法把意图中的范围对应到自己有权替换的那一段，就整笔拒绝。能否从宿主读回当前预编辑范围，未知。

### 3.3 事务

一笔事务处理一条意图，检查按下面的顺序。任一项失败：不调用宿主写入，会话记录里的「已应用提交 / 自有区间」也不前进。

1. 意图的会话标识等于这一份开放记录的标识。别的标识不修改这一份记录。
2. 寿命是开放，不是已关闭。
3. 交付许可是允许。
4. 当前字段标识等于打开时的快照。
5. 宿主当前接受写入。
6. 已应用提交为否。同一会话的提交意图至多成功一笔。
7. 种类为预编辑时：这条意图呈现的假设，是假设链上尚未被更晚已呈现假设盖过的那一条。它修订的若是更早的假设，而更晚的修订已经呈现过，则拒绝。识别流里的旧文本仍保留，只是不再写字段。
8. 种类为提交时：字符串来自呈现。呈现在改写结果为「不替换」时使用假设原文，在「替换为这段文本」时使用替换文本。交付不调用改写流，也不在改写结果仍为「未到」时自己造一段优化文本。

应用预编辑：自有区间的可观察文本变为意图字符串；已应用提交仍为否；文档中已有的提交文本不变。

应用提交：该范围的可观察文本变为意图字符串，并且不再处于预编辑；自有区间变为无；已应用提交变为是。这笔是该会话最后一笔成功的交付。

原语 7 允许呈现在改写未到时继续发预编辑意图。事务的第 8 项只约束提交意图，不把「先预编辑、改写结束后再提交」写进检查。那是呈现配对，见第 4 节。

### 3.4 状态迁移

会话寿命与两位标记的迁移如下。未列出的输入不迁移。

| 当前 | 输入 | 迁到 | 字段 |
| --- | --- | --- | --- |
| 未建立 | 触发给出打开，且当时能记下字段标识与范围快照 | 开放，允许交付，收束未请求 | 不动 |
| 未建立 | 打开时字段标识记不下来 | 保持未建立 | 不动 |
| 开放，允许交付 | 触发给出关闭 | 仍开放，允许交付，收束已请求 | 不动。关闭信号本身不写字段 |
| 开放，允许交付 | 字段标识偏离快照 | 仍开放，拒绝交付 | 不动。不改写新字段，也不再改写旧字段。已写进文档的提交文本保持。已经显示着的预编辑区间也不在这一迁移里被清除 |
| 开放，允许交付 | 失焦信号，且触发不把它当成关闭，字段标识也未偏离快照 | 不迁移 | 不动。失焦不是标识 |
| 开放，允许交付 | 失焦信号，且触发把它当成关闭 | 与「触发给出关闭」相同 | 不动 |
| 开放，允许交付 | 预编辑事务成功 | 寿命与许可不变；自有区间更新 | 只有自有区间被替换 |
| 开放，允许交付 | 提交事务成功 | 然后进入已关闭 | 该范围成为提交文本，预编辑副本不保留 |
| 开放，拒绝交付 | 任意识别假设或改写结果 | 寿命可保持开放 | 不动。结果留在会话记录里 |
| 开放，且收束已请求，允许交付 | 呈现不再持有未发出的提交意图，且自有区间为无，且已应用提交为是或假设链为空 | 已关闭 | 不动 |
| 已关闭 | 任何迟到的假设、改写或意图 | 保持已关闭 | 不动 |

「呈现不再持有未发出的提交意图」这一句依赖第 4 节的呈现配对：收束已请求之后，若改写尚未返回，呈现仍持有待发的提交，寿命就保持开放。本文不另给一个时钟去结束这种开放。

标识不一致的结果：不进入上表的任何一行，当前会话的各位不变，字段不动。

同一字段上第二枚会话请求打开时：原语 1 只禁止它们写进彼此的范围，并不禁止两枚同时允许交付。宿主文本客户端的预编辑在距离节所见的调用形状里是该客户端上的一次替换写入。候选迁移是：该字段上已有一枚允许交付的开放会话时，新的打开不获得允许交付，旧会话也不因此被关闭。否则新会话没有一笔自己的事务可用来结束旧会话留在字段上的预编辑，旧会话若被直接关闭又不能再写。这一迁移是候选，不是原语 1 的原文。

### 3.5 与键盘路径的共存约束

键盘路径的输入仍是键盘事件，输出仍是键盘自己的组合预编辑与键盘自己的提交。语音侧不向该路径提交采样帧、假设、改写结果或变更意图，也不调用该路径来读取「语音进行到哪一步」。

触发对键盘事件只有两个结果：

- 取走。该事件不进入键盘组合。取走只用于产生某一会话的打开或关闭。取走不写字段。
- 不取走。事件的类型与修饰保持原样，准备进入键盘链。

共存约束作用在「准备进入」与「实际进入」之间，不作用在键盘链内部：

- 若当前没有任何语音会话登记着自有预编辑区间，未取走的事件立刻原样进入键盘链。
- 若有自有预编辑区间，未取走的事件停在键盘链之外，事件内容不改。呈现可以为此发出一条意图来结束该区间：要么一条提交意图，要么一条把自有区间替换为空字符串的预编辑意图。交付在会话仍允许时应用它。应用成功后，事件再原样进入键盘链。
- 呈现不发出这条意图，事件就保持未进入。本文不把「停住」换成超时后强行进入，也不在键盘链里加一条忽略语音区间的分支。
- 结束区间用提交还是用空预编辑，是呈现的选择，不是触发的权利，也不是键盘组合的状态。

由此得到一个候选后果：在自有预编辑区间还在时，包括修饰键在内的未取走事件都先停在键盘链之外。不能先跑一遍键盘链来区分「这枚键会不会改预编辑」，因为跑一遍就已经进入了组合。

另一个候选后果：自有区间尚未出现时，未取走的键会立刻进入键盘链，键盘路径可以写下它自己的预编辑。此后语音事务若仍按允许交付去写同一字段，两方会交替替换宿主上的那一段。原语 1 没有把「键盘链已被进入」列为拒绝原因。本文的候选倾向见第 4 节，反论一并写在那里。

键盘路径自己在失焦时如何处置它自己的组合，仍由键盘路径执行。语音会话不订阅这次处置当作自己的提交。若这次处置碰巧写了宿主字段，语音侧此后无法再证明自有区间仍是自己留下的那一段：对应的语音事务按第 3.3 节「范围无法对应则拒绝」处理，而不是把键盘路径改成先询问语音会话。

## 4. 当前倾向（候选）

候选倾向如下。

会话状态机采用第 3.4 节的表。触发收束与会话关闭是两位。字段偏离快照只把交付许可改为拒绝，不销毁假设，不把写入改道到新字段，也不在旧字段上补一笔清理。失焦先交给触发；触发不消费它，会话就不因为失焦这一件事关闭。

呈现与事务的候选配对沿用 007 第 4 节，并收成可以核对的发出规则：

- 部分假设只产生预编辑意图。三条部分假设至多三笔预编辑事务，零笔提交事务。
- 改写结果未到时，呈现不发出提交意图，也不编造优化文本。预编辑上可见的仍是识别假设自己的文本。
- 收束已请求之后，改写结果若为「不替换」，至多一笔提交事务，字符串是假设原文；若为替换文本，这一笔使用替换文本。
- 提交事务成功之后会话进入已关闭。此后的部分假设只留在假设链上。
- 收束已请求、假设链为空、自有区间为无：不写字段，会话进入已关闭。
- 收束已请求、自有区间仍在、改写结果仍未到：会话保持开放且允许交付，字段保持该预编辑。本文不补一个结束钟点。

交付只执行上述意图。通道仍是「宿主文本客户端能接受的预编辑写入或提交写入」这一种形状；宿主拒绝时是否还有别的通道，不在本篇给定，意图的四字段也不因此增加。

键盘共存的候选倾向是第 3.5 节的约束：不修改键盘链；不把语音文本灌进组合；自有预编辑区间存在时，未取走的事件等语音事务自己结束该区间后再进入。同一字段标识上至多一枚会话处于允许交付。

反论一：有的宿主在说话结束时就期望文档里已经有字。把提交留到改写返回，这段时间里用户若把字段发出去，迟到的提交会因字段变化或会话拒绝而不出现。007 已记下这一反论。本篇的状态机允许呈现改发另一种序列（例如收束时先提交假设原文，改写结果到达后不再写），事务检查仍然成立。目标宿主在端点之后还留不留得住预编辑，未测量，所以本段配对只保持候选。

反论二：未取走的键在预编辑还在时被停住，用户会觉得语音期间键盘没有原样可用。若改为立刻进入键盘链，未修改的键盘路径会用它自己的预编辑或提交替换字段上的字，语音假设可能未经提交事务就变成文档文本，或未经会话决定就被抹掉。这两侧不能同时满足。本篇倾向停住事件、保持键盘链不分支；「停住是否可接受」没有用户侧测量。

反论三：出字之前的那一枚未取走键若立刻进入键盘链，随后的语音预编辑会和键盘预编辑抢同一段字段。把「键盘链已被进入」追加为拒绝原因，可以让语音侧停写，但这不是原语 1 的原文。本篇倾向在这种情况下改为拒绝交付、假设保留、键盘链继续；反论成立与否取决于用户是否把那一枚键当作「这轮语音还要继续写」。未测量，因此这一拒绝原因标为候选追加，不回写成原语 1 的不变量。

反论四：同一字段只允许一枚交付中的会话，会拒绝重叠的第二次打开。原语允许两枚会话只要范围不相交。若宿主实际能同时保留两段预编辑，这一倾向就过窄。现行调用形状没有表现出多段预编辑，也没有证明宿主不能。倾向保持候选。

## 5. 仍然未知的点

下列各项缺证据。本文不补猜测，也不把缺证据写成一种待选策略。

1. 宿主字段标识在目标输入法客户端上是哪一个可比较的值：未知。应用包名比字段粗，同一应用里换一个输入位置未必换包名。控制器实例是否在失焦之后仍只对应原来的字段，未测量。
2. 一段失焦、权限提示或状态栏交互，是否等于字段标识偏离快照：未知。007 记下样本里有按时间过滤瞬态失焦的做法，阈值未知。本篇不取一个数，状态机里失焦与字段偏离是两行不同的迁移。
3. 目标宿主在识别端点或触发收束之后，是否仍把预编辑留在字段上直到提交事务：未知。这决定第 4 节候选配对的反论一是否成立。
4. 触发具体采用哪一种开闭条件：未知。若干宿主不把普通键的松开经输入法键盘事件送回，因此「以松开为关闭」不能只靠这条事件路径。条件未选，检测路径也未选。
5. 交付时能否读回宿主当前预编辑范围，用来核对会话自有区间：未知。读不回时，第 3.3 节的范围对应检查没有可观察的输入，事务只能依赖会话自己登记的区间。登记与宿主真实区间不一致时会怎样，未测量。
6. 键盘路径在语音预编辑已经显示时，若因失焦执行它既有的组合处置，宿主字段上的预编辑会变成键盘原始编码、空字符串，还是保持不动：未知。本篇因此不把那段既有处置当成语音提交。
7. 改写结果一直不到达、自有预编辑仍在字段上时，会话以外的哪一个事实能让寿命进入已关闭：未知。本篇不引入一个钟点。
8. 用户在自有预编辑仍在时敲下的未取走键，呈现应发出提交意图还是空预编辑意图：未知。事务两种都接受，共存约束只要求在进入键盘链之前由语音事务结束该区间。
9. 出字之前的未取走键是否表示这轮语音应停止写字段：未知。第 4 节反论三的候选追加依赖这一点。
10. 同一宿主字段能否同时持有两段互不覆盖的预编辑：未知。第 4 节「一字段一枚允许交付的会话」依赖「现有写入是一次替换」这一观察，不是对宿主能力的测量。
11. 按公共前缀只重绘预编辑后缀，哪些宿主会因整段替换预编辑而搅动撤销记录：未知。007 已说明这不是原语 7 的不变量。本篇事务的可观察结果是整段自有区间等于意图字符串，不规定通道内部是否只重绘后缀。

007 已列出、本篇不重复展开的缺口：离线模型与云端接口在官方进程之外有无可调用契约；云端接口是否同时提供识别与改写；个人词与键盘用户词是否同一存储；识别所要求的采样格式数值。那些缺口不改变本节的会话记录与事务形状；契约未知时，对应角色空着，会话与事务仍可用不写字段的替身核对。

### 6.2 键盘路径实际在做什么

键盘链是一条直线：`handle` 把 `.flagsChanged` 与 `.keyDown` 译成键盘码，调用 `processKey` `402`，其中 `412` 行调用 `rimeAPI.process_key`，再进入 `rimeUpdate` `448`。`rimeUpdate` 在 `452` 行调用 `rimeConsumeCommittedText`（函数体 `437-445`：`get_commit` 返回真且 `text` 非空才 `commit`），再按键盘上下文 `show` 或 `showPanel`。这条链上没有语音会话判断。这是「键盘路径尚未被改写」的现状，不是第 3.5 节的闸门已经存在。

```swift
// 源：dev-docs/refs/code/squirrel/sources/SquirrelInputController.swift:163-165
  override func recognizedEvents(_ sender: Any!) -> Int {
    return Int(NSEvent.EventTypeMask.Element(arrayLiteral: .keyDown, .flagsChanged).rawValue)
  }
```

已登记事件只有按下与修饰键变化。现状因此不能从输入法键盘事件里观察普通键松开。第 5 节第 4 点的平台限制在这棵树上仍然成立：这里没有任何语音触发去消费松开，也没有任何别的监听补上松开。

```swift

      if modifiers.contains(.command) {
        break
```

`.keyDown` 里只有 Command 在进入 `processKey` 之前被放行，`handled` 仍为初值假，函数在 `123` 行返回该值。Option 没有这条分支。005 第 3.2.3 节写的是 Command 与 Option 一并放行，与现行 `96-99` 不符。距离测量不能把 Option 当成已经让出的触发空位。

失焦时的键盘处置与语音提交不是一回事：

预编辑与提交的现行写入共享控制器上的一份缓存：

`replacementRange: .empty` 的定义是 `NSRange(location: NSNotFound, length: 0)`，见 `BridgingFunctions.swift:58-60`。`show` 在缓存相同的时候不调用 `setMarkedText`；真正的 `setMarkedText` 在 `605`。`activateServer` `191` 只把本地 `preedit` 置成空字符串，不在这一行写宿主。因此这份 `preedit` 是键盘界面去重缓存，不是会话自有区间，也不是假设链。语音意图若复用 `show` / `commit`，会改写这份缓存：下一次键盘 `show` 可能因缓存相等而跳过宿主更新，或在 `commit` 时被清掉。现状没有第二条不经过这份缓存的字段写入。

`rimeUpdate` 也不存在 005 所写的「提交后若预编辑为空则 `clearMarkedText`」。现行 `commit` 只在键盘选项 `force_marked_text_for_direct_commit` 为真、本地 `preedit` 为空且字符串非空时，先 `setMarkedText` 再 `insertText`（`572-581`）。这是键盘直接上屏的兼容分支，不是语音事务的「先预编辑再提交」。

`show` 本身不查询光标矩形。候选窗位置来自 `showPanel` `611-612` 的 `client.attributes(forCharacterIndex: 0, lineHeightRectangle:)`。005 第 3.3.2 节描述的「先 `setMarkedText` 再两次 `firstRect`」不在现行 `show` 里。距离上，现行树没有为语音预编辑单独测量光标；也没有第 3.2 节那种与写入分开的范围核对。

并击超时函数 `onChordTimer` `315` 在 `320` 行把已经进入键盘组合的键再合成一次带释放掩码的 `process_key`。那是键盘组合的补发，不是物理松开事件，也不能当作语音触发的关闭信号。

### 6.3 距离不等于设计

现状没有第 3 节的会话记录、事务检查和键盘链外闸门。`handle` 在更新客户端指针之后就进入 `switch event.type`（`47-54`），中间没有「取走则不进入 `processKey`」的语音触发。`commit` 与 `show` 是键盘交付的直接调用，不是意图的执行器。把语音字符串送进这两个函数，或送进 `commitComposition`，都会让语音文本经过键盘会话或键盘预编辑缓存。这是缺口，不是本篇倾向里的通道。

005 第 4 节把协调器、热键分流、复用 `show`/`commit`、复用候选窗、在 `deactivateServer` 里取消异步任务写成五个挂载点。那些段落自己标的是待确认候选，而且行号锚在旧快照上。本篇的距离只承认第 6.1 节表里那些在现行行号上仍能点到的事实；不把「在某个旧行号前插入语音分支」收成会话状态机。
