# 011-derivation-voice-context-memory：语音优化的上下文记忆

本文只推导一件事：修正对、个人热词、光标前文、宿主应用信息，怎样在一次语音优化里汇成同一份上下文，以及这份上下文交给本地模型槽位和云端优化请求时各长什么样。倾向一律是候选。样本只用来核对数据落点，不把样本内部的提示词模板或私有请求写成可调用接口。

用户点名的是语音优化输入的接口。上下文在这里是会话之外的事实，不是麦克风里的采样帧，也不是识别假设本身。

## 1. 推理链

### 1.1 为何是一份快照，而不是两套记忆

`007` 的原语 6 把上下文定义为一次只读汇集：来源在该时刻的值收成槽位快照，同一份快照可以同时交给识别流与改写流。快照是名字到文本，不是某一个模型的提示词格式。来源读不到时，对应槽位缺席，快照仍然成立。

样本里这四件事实确实被收成同一束，再落到两个所在地：

- 本地模型侧，`flute::asr::ntp_cif::PromptProcessor` 把结构化上下文填进具名槽位，再交给端侧解码。`003` 记下的槽位里，与本文四件记忆对应的是 `USER_MODIFY`（修正对）、`HOTWORDS`（个人热词）、`CUR_CONTEXT`（光标周围文本）、`BOT_DESC`（宿主场景描述）。
- 云端侧，`004` 记下 `DoubaoIme.ASRGlobalContext`：由 `context.db` 的召回生成，同时供给云端识别首包、`SmartOrganizeClient` 与本地 `Flute`。优化请求这一路的承载对象是 `DoubaoIme.ASRSmartOrganizeContext`，其中出现了光标前文 `precedingText`、宿主 Bundle ID、输入框角色、个人纠错对。

因此本文的方向是：会话持有一份槽位快照；本地槽位填充与云端优化请求各自做投影。投影可以改名、拼接、按该制品声明的长度截断，但不重新召回，也不改快照里的文本。

若改成「本地一套召回、云端另一套召回」，两边会看到不同的对和不同的词，原语 6 的「同一份快照」就不成立。样本用一个 `ASRGlobalContext` 供给多条路径，说明分开召回不是它实际走过的分法。

### 1.2 四件记忆为什么分成四个槽，而不是一条提示词

四件事实的来源和更新时机不同。

| 记忆 | 样本里的来源 | 相对一次语音会话的时间 |
| --- | --- | --- |
| 修正对 | `context.db` 的 `modify_pair`：`src_text` 与 `dst_text` | 跨会话留下。样本在用户把识别片段改成另一段文本时更新 |
| 个人热词 | `context.db` 的 `user_word`：`word` | 跨会话留下。样本从输入文本里抽出专有名词后更新 |
| 光标前文 | 当前输入框光标之前已提交的文本 | 属于这一次打开的宿主字段。会话之间不保留 |
| 宿主应用信息 | 宿主应用标识；优化上下文里还出现输入框角色 | 属于这一次打开的宿主字段。应用标识在字段打开时即可读到 |

`007` 已舍弃焊法 D：上下文若只活在某一个模型的提示字符串里，换模型就要重写来源，识别与改写也无法共享同一束事实。本文沿用这道取舍，并落到数据上：快照层不出现 `GPT2Tokenizer` 的 token id，不出现 `pre_prompt` / `post_prompt`，也不出现云端那一条 POST 的报文。那些是投影之后的东西。

原语 6 写「名字到文本的映射」，为的是排除提示词格式。修正对和热词不止一条。候选把一个槽的值放宽成「一段文本，或有序的若干段文本」：每一段仍是文本，顺序属于快照。若在快照层就用分隔符拼成一条长字符串，分隔符会变成契约；样本只露出配置键 `user_modify_delim`、`user_modify_pair_delim`、`hotword_delim`、`cursor_context_delim`，字符本身未见。拼接留在投影里。

### 1.3 舍弃的组成方式

**舍弃把识别假设写进记忆。** 原语 5 的输入是「一条识别假设 + 上下文快照 + 会话标识」。假设是本会话的产出。`004` 里优化请求体同时带有原始 ASR 文本、光标前文、宿主应用信息、会话 ID。其中只有光标前文和宿主应用信息是记忆；原始 ASR 文本是假设，会话 ID 是原语 1 的标识。云端那一个报文是这三样的投影叠在一起，不是快照本身。

**舍弃把声学槽当成记忆。** `PromptProcessor` 还有 `AUDIO`，来自采样帧经编码器与 CIF 之后的嵌入。它随帧变化，不是会话外事实。本地投影不从这份快照填 `AUDIO`。

**舍弃 `DIALOG` 与 `BOT_NAME`。** `003` 的槽位表有 `DIALOG`（近期对话），架构图的组装行却是 `[BOT_NAME/DESC] + [USER_MODIFY] + [HOTWORDS] + [CUR_CONTEXT] + [AUDIO]`，两处对 `DIALOG` 是否进入组装不一致。本文点名的四件记忆里没有独立的对话记录；光标前文不是对话记录。`BOT_NAME` 在 `003` 里是助手身份，不是宿主应用标识。两者都不进入这份快照。

**舍弃把本次预编辑读回光标前文。** 预编辑是本会话识别假设的呈现。汇集若发生在预编辑已经写入之后，假设会把自己当成语境，本地槽位与云端请求会一起放大这段尚未定稿的文本。候选在会话打开时汇集，读的是打开瞬间光标之前的已有文本。

**舍弃在快照里携带召回计数、时间戳和库内密文。** 样本的 `use_count`、`recall_count`、`update_at` 参与修正对的挑选；挑选之后进入 `USER_MODIFY` 的是 `src_text -> dst_text` 的文本。`key_version = 1` 时明文列只剩 `#<id>` 占位，真实文本在密文列。快照要的是挑选之后的明文。密文格式、盲索引和密钥派生不是优化请求的字段，本文不把它们写成契约。

**舍弃把来源的写入器放进这次请求。** 原语 5 规定改写流的输出不含「去更新上下文来源」的指令。样本在最终文本命中 `dst_text` 时调用 `UpdateDstTextRecallCount`，那是来源自己的计数，不是优化请求的往返字段。分词、逆文档频率、命名实体识别与拼音表是样本用来生长 `user_word` 的路径，同样不是一次优化请求的形状。图消解（传递链、同源留新、双向互逆）发生在召回之前；快照只看见消解之后的有序结果。本文不另写一套写入、清洗或回写。

**舍弃端云各写一份来源。** 见 1.1。替换来源集合时，两个流收到的仍是快照，这是原语 6 的不变量。

### 1.4 样本在进入槽位之前如何挑选修正对与热词

挑选是来源的事，不是快照类型的事。记下它，只为说明快照里的列表为什么不是「库里的全部行」。

`003` 记下：每次构建提示时，`QueryModifyPairTopN` 的默认 `total_limit = 50`，`QueryUserWordTopN` 的默认 `limit_num = 100`。修正对不是单一排序，而是三段配额：

1. `TodayTop30`：当日零点以来更新过的对，按 `use_count DESC, update_at DESC`，最多 30 条。
2. `RecallTop10`：排除已选的 `src_text_tag` 之后，按 `recall_count DESC`，最多 10 条。
3. `Remaining`：其余名额 `50 - 当日实际条数 - 召回实际条数`，按 `use_count DESC, update_at DESC` 补齐。

进入提示之前还经过内存侧 `ApplyReplaceRules`。样本另外会删掉创建超过 30 天的对，并按互逆对、同源多目标和传递链清理。热词侧记下的是按时间与频次索引召回，默认上限 100，没有与修正对相同的三段配额描述。

这些数字是该样本的默认上限，不是本快照的类型约束。候选只固定一件事：一次汇集产生一份已经挑选好的有序列表；两个投影消费这一份，可以按制品声明的长度从同一顺序上截断，不在投影里再排一次序。`user_modify_max_length`、`hotwords_max_length`、`cursor_context_max_length`、`bot_desc_max_length` 这些键在样本里存在，数值未见，本文不补。

光标前文与宿主应用信息不经过上述配额。它们是这一次字段上的只读值，没有「Top-N」这一说。读不到则为缺席。

## 2. 与 007 原语的对应关系

| 原语 | 本文如何对应 | 本文不改动的类型 |
| --- | --- | --- |
| 原语 6 上下文 | 四件记忆是来源。输出是一份槽位快照。本地槽位与云端优化字段都是这份快照的投影 | 快照不是提示词，也不是权重 |
| 原语 4 识别流 | 输入里的「上下文快照」就是这份。本地模型若担任识别流，只接收投影后的槽位，外加采样帧；帧不在快照里 | 空快照仍然只消费帧并产出假设 |
| 原语 5 改写流 | 云端优化请求是「假设 + 这份快照 + 会话标识」的投影。假设与会话标识贴在请求上，不写进槽位 | 改写输出仍是「不替换」或「替换为这段文本」，不含更新来源的指令 |
| 原语 1 会话 | 打开时的宿主字段标识、范围快照，与本文的宿主文本、光标前文同时刻读取，但是不同的值。范围用于交付判定；前文文本用于优化 | 字段标识变化则拒绝交付，不改快照的定义 |
| 原语 9 绑定 | 槽位名与报文字段名属于适配器。样本内部的 `USER_MODIFY` 等名字是观察到的落点，不是已经能在官方进程之外调用的契约 | 契约未知时适配器不成立，不改快照的形状 |

原语 6 允许来源集合为空。四槽全缺席时，快照仍成立，识别流与改写流按各自的输入类型运行。原语 6 允许的来源写法是「光标周围文本」；本文放进共享快照的是光标前文。云端优化侧被点名的是 `precedingText`。光标之后的文本是否进入 `ProcessCursorContext`，两份笔记没有分开的证据，不单列槽位。

原语 6 还写明：个人词、纠错对与键盘路径上已有的用户词是不是同一存储，未知；原语不规定存储。本文同样只规定快照与两份投影，不规定这四件记忆落在哪一个文件里。

汇集是只读的：一次汇集不修改宿主字段，不修改键盘组合，不修改模型权重。这与原语 6 的核对句一致。

## 3. 数据契约与状态迁移

下列形状是候选。它描述会话内交换的数据，不描述库表，也不描述官方进程内部的报文编码。

### 3.1 快照

一次汇集的结果是不可变的值。槽位缺席用「没有这个槽」表示，不用空字符串顶替。空字符串会让投影分不清「宿主给了空文本」和「没有读到」。

| 槽位 | 值 | 缺席 |
| --- | --- | --- |
| `host_app` | 一段文本：宿主应用标识。样本云端侧见到的标识是 Bundle ID | 客户端给不出标识 |
| `field_role` | 一段文本：输入框角色。`ASRSmartOrganizeContext` 列出了这一项，与 Bundle ID 分开 | 读不到角色 |
| `cursor_before` | 一段文本：汇集瞬间、光标之前、已经在字段里的文本。不含本会话的预编辑 | 宿主不提供周围文本 |
| `hotwords` | 有序词文本。顺序是这次召回的顺序 | 来源没有词 |
| `corrections` | 有序对。每对是两段文本 `(src_text, dst_text)`，表示「听到或写下 src 时，曾经被改成 dst」 | 来源没有对 |

`corrections` 进入快照之前，候选要求列表已经满足样本消解后的形状：同一个 `src_text` 至多一条 `dst_text`；不同时包含一对和它的反向对；传递链上不保留较旧的一跳。不满足时，两个投影会一起收到互相矛盾的替换。计数、时间戳、盲索引不进入槽位。

`host_app` 保存标识文本，不保存「这个应用应该用什么口吻」的生成句。样本本地槽 `BOT_DESC` 的取值被描述为场景描述，那是投影可以把标识渲染成的句子，不是快照里的第二份事实。

### 3.2 状态迁移

```text
来源（跨会话留存，本文不规定其存储）
        │ 会话打开时只读汇集一次
        ▼
快照（本会话内固定；槽位可缺席）
        ├─投影─▶ 本地模型槽位
        └─投影─▶ 云端优化请求中的上下文字段
改写结果与识别假设 ──不写回──▶ 快照，也不写回来源
```

1. 未汇集。会话尚未打开，或一次读还没做完。两个流都还没有快照。此时没有「半份热词、半份前文」。
2. 已汇集。四次读取都有了结果（值或明确缺席）。快照固定。本会话内识别流与改写流只读这一份。
3. 投影。适配器读快照，写出槽位文本或请求字段。投影不写回快照，不写回来源。
4. 会话结束。这一份快照可以丢弃。来源不因会话结束而被改写。下一次会话若来源变了，得到的是另一份快照。

候选不在改写发出前按当时的预编辑再汇集一次。若实现上另做一次只读读取，那是另一份快照，仍然满足原语 6，但光标前文的来源会被本会话的预编辑污染。样本在 `StartTask` 首包与优化请求两处都放了上下文，是否各读一次、两次字节是否相同，笔记没有测量，见未知。

打开瞬间同时读取的范围快照（原语 1）不进入上表。它不是槽位。

### 3.3 本地模型槽位投影

投影的输入是快照。输出是样本内部槽名到文本的对应。`AUDIO` 不在此列。分隔符与最大长度由该制品的配置决定；字符与数值未知，故投影只规定「沿快照的顺序拼接，超长则从同一顺序截断」。

| 快照槽 | 样本内部槽 | 投影 |
| --- | --- | --- |
| `corrections` | `USER_MODIFY` | 按快照顺序写成 `src_text -> dst_text` 的文本序列。样本用 `user_modify_delim` 与 `user_modify_pair_delim` 分隔，具体字符未知 |
| `hotwords` | `HOTWORDS` | 按快照顺序的词文本。样本另有 `hotwords_types` 与 `hotwords_types_prompts`，类型枚举未见，投影不发明类型 |
| `cursor_before` | `CUR_CONTEXT` | 原样文本。样本对该槽的描述是光标前后，本投影只放入前文 |
| `host_app` | `BOT_DESC` | 标识文本。是否再渲染成场景句，取决于该制品的槽约定；快照不因此多出一个槽 |
| `field_role` | （无同名槽） | 样本没有把输入框角色单独记成 `PromptProcessor` 槽。角色可附在 `BOT_DESC` 的文本里，也可在该制品不接受时省略。省略不从快照删除 |
| — | `BOT_NAME`、`DIALOG`、`AUDIO` | 不从这四件记忆填充 |

这些槽名位于官方进程内部的 `PromptProcessor`。官方进程之外能否按这些名字喂入，未知。表内是观察到的数据落点。可调用契约不存在时，按原语 9，适配器实例不成立，槽位投影没有可核对的写入。

### 3.4 云端优化请求投影

云端优化请求对应原语 5，不是识别首包。`004` 把优化这一路记为 `SmartOrganizeVoiceCoordinator.coordinate(asrText, context: ASRSmartOrganizeContext)` 之后，由 `SmartOrganizeClient` 发出的 `text_organization` 请求。已见证的载荷成分是：原始 ASR 文本、光标前文 `precedingText`、宿主应用信息、会话 ID `requestID`。`ASRSmartOrganizeContext` 的字段说明另外列出输入框角色与个人纠错对。

候选的逻辑形状如下。缺席的槽不出现在 `context` 里。此处不是观察到的 JSON 键名；键名未知。

```text
optimize_request:
  hypothesis: 文本          # 原语 5 的识别假设，不是记忆
  session_id: 文本          # 原语 1，不是记忆
  context:
    preceding_text: 文本    # ← cursor_before
    host_app: 文本          # ← host_app
    field_role: 文本        # ← field_role
    corrections:            # ← corrections，顺序与快照相同
      - src_text, dst_text
    hotwords:               # ← hotwords；是否被该请求接受，见下
      - 词文本
```

`hypothesis` 与 `session_id` 贴在请求上，因为原语 5 的输入本来就有这两项。它们不是上下文槽。本地槽位投影不接收 `hypothesis`：假设是识别流的输出，不是它的记忆输入。两边相同的只有快照里那些槽的文本和顺序。

热词的证据粒度不够，不能写成已见证字段。`004` 第 4 节写 `ASRGlobalContext` 向 `SmartOrganizeClient` 提供 `user_word`；同文第 3.2 节对请求体的列举没有热词。识别首包的 `extra` 则明确包括热词、纠错对与宿主应用上下文，但那是识别路径，不是优化请求。候选把 `hotwords` 留在快照里，并允许优化请求的投影在制品契约接受时带上同一顺序的词；契约不接受则该投影省略这一项。不因此做第二次召回。

识别首包的 `extra` 若在同一次会话里也要上下文，它投影同一份快照。那是原语 4 的绑定，不是第二份记忆。`extra` 的 JSON 键名未见。

官方进程之外，这条请求的鉴权与报文字段能否原样成立，未知。投影只定义逻辑字段。适配器不提取令牌、不复刻签名、不伪装官方进程。契约只存在于官方进程内部时，这一侧的适配器同样不成立。

## 4. 当前倾向（候选）

一次语音优化持有一份上下文快照，在会话打开时只读汇集，本会话内不再改。快照有五个槽：`host_app`、`field_role`、`cursor_before`、`hotwords`、`corrections`。后两个是有序文本；前三个各是一段文本。任一槽可以缺席。修正对与热词在进入快照前已由各自来源挑选完毕，快照不带计数、时间戳和密文。

本地模型槽位与云端优化请求是这份快照的两个投影。本地投影落到样本内部的 `USER_MODIFY`、`HOTWORDS`、`CUR_CONTEXT`、`BOT_DESC`，不填 `AUDIO`、`BOT_NAME`、`DIALOG`。云端优化请求在假设与会话标识之外携带同一份前文、宿主标识、输入框角色与修正对；热词仅当该请求的契约接受时按同一顺序附上。投影可以截断，不可以重排，不可以把缺席写成空字符串。

改写结果不写回快照，也不写回来源。来源跨会话如何生长，不属于这次请求的形状。

## 6. 与 Squirrel 的距离

本节只写当前源码与这份快照之间的距离，不是接法。

宿主应用标识已经能读到。`SquirrelInputController.handle` 在每次按键时调用 `client?.bundleIdentifier()`，与 `currentApp` 比较后调用 `updateAppOptions()`；`createSession()` 在标识缺失时使用 `UnknownApp` 加计数的替身字符串。`updateAppOptions()` 用该标识选取 `getAppOptions` 的键盘选项；仅当配置 `unsafe/report_bundleid` 为真时，才把同一字符串写入 Rime 会话属性 `client_app`。距离：标识停在键盘会话的选项与属性上，没有进入语音优化快照，也没有 `field_role` 槽。

光标前文没有被读取。`SquirrelInputController.swift` 对 `IMKTextInput` 的调用是 `setMarkedText`、`insertText` 与 `bundleIdentifier`，没有 `selectedRange`，也没有向客户端取 `attributedSubstring(from:)`。`SquirrelPanel.swift` 里的 `attributedSubstring(from:)` 作用在面板自己的标签字符串上，不是宿主字段。距离：不存在 `cursor_before` 的来源读取。

修正对与个人热词没有对应的召回。仓库内的 Squirrel 与 `librime` 接口索引里没有 `modify_pair`、`user_word`，也没有把用户词投影到 `USER_MODIFY` 或 `HOTWORDS` 的代码。键盘用户词典是否能作为 `hotwords` 的来源，仍是第 5 节第 9 条，距离上只确认「现在没有这份投影」。

本地槽位投影与云端优化请求投影都不存在。当前进程没有 `PromptProcessor` 槽填充，也没有 `text_organization` 一类请求的字段组装。
